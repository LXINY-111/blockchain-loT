## 1. 本次结果与判断

**100,000 条原记录生成了 100,000 笔积分交易，涉及 593 个首次放置状态。其中 395 个状态实际被多个设备访问，且这些设备确实分布在不同分片；这 395 个状态承载了 94,230 笔交易。**

同样这 100,000 条记录，在旧定义中涉及 1,162 个状态，实际被多个报告设备访问的状态是 0 个。这里比较的是访问结构，不是算法效果：新旧状态含义、交易金额和任务边界不同，不能将它们的跨片率之差写成算法收益。

结论是：**共享任务语义的数据生成与读取检查通过，可以进入小规模放置规则验证。尚不能断言容量规则有效、PPO 必要或论文创新足够。**

## 2. 为什么选这版规则

采用一个容易解释的应用假设：平台每小时发起一轮“设备网络活动记录采集任务”，向登记设备收集记录；每组每轮使用独立积分账户，每条贡献获得 1 积分。

一小时与每组四台是这版工程样例的公开假设，不是从真实业务恢复出来的事实，也不是优化搜索的结果。选择它们是为了先验证有限成员、持续贡献、定期出现新任务的最小结构。**没有按跨片率、分片布局、未来活跃度或 PPO 输赢调整分组与周期。**

这版完整规则已在生成前写入项目外的 [rules.json](C:/Users/HONOR/.codex/visualizations/2026/09/05/01a07180-b5e5-7663-9340-bc0bf9f9978d/shared_task_sample_v1_20260909/rules.json)，生成后核对规则散列未变。

| 要素 | 冻结规则 |
|---|---|
| 应用语义 | 网络活动采集任务的共享积分账户；链上拟执行普通账户转移 |
| 设备名单 | 现有名单中的 27 台，视为预登记设备；不读取全量访问频率来选成员 |
| 分组 | 固定种子 `20260909`；按 `SHA256(seed + "\u007c" + 小写设备名)` 排序后每四台一组；共六组四台、一组三台 |
| 分组依据 | 只用登记设备标识；不使用设备分片、网络端点、未来交易或算法输出 |
| 任务创建 | 每个原记录日历整点、每组一项新任务；开始时间包含、下个整点排除 |
| 任务寿命 | 一小时；组成员在这版中保持不变 |
| 状态键 | `应用标识 + 小时轮次 + 组标识 + credit-account` |
| 一条贡献 | 一条有效原记录生成一笔 `任务账户 → 本条记录的设备`、金额为 1 的积分交易 |
| 多种协议 | 同组同一小时的 DNS、HTTP 等记录均属于该轮采集；协议保留为来源，不决定共享关系 |
| 新状态口径 | 任务第一条贡献到达才激活一个新状态；这里只统计应有的放置次数，没有运行放置器 |
| 无贡献任务 | 保留登记元数据；不算已放置状态，不凭空补交易 |
| 未知设备 | 若以后出现不在名单中的设备，使用私有小时任务并记录回退；本样例回退为零 |
| 已知参与者 | 注册名单和均匀先验；名单四人不代表四人未来都实际贡献 |
| 账户预算 | 每任务固定名义预算 10 亿积分；本次仅为元数据检查，不代表已完成链上初始化或资金划拨 |
| 额外交易 | 本次不增加任务创建/结算交易，任务注册表在链外；后续如增加必须单独计数 |
| 样本窗口 | 前 100,000 条，原 `tx_index ∈ [0,100000)`；属于旧训练前缀，明确用于开发 |
| 分片口径 | 16 分片，设备地址沿用现有哈希归属；仅在分组后用于描述统计 |

这里的“每小时新账户”对应新采集轮次，不是运行中将一个热点账户拆开。若未来业务需要跨小时共享同一个持续状态，必须另立语义版本，不能继续用本规则冒充该业务。

随机分组代表构造的任务编组，不证明这些设备位于同一真实家庭、网关或组织。任务注册、积分规则、组成员是仿真增强；原数据提供设备事件与时间顺序。称为“真实轨迹驱动的构造任务数据”更准确。

## 3. 时间含义和边界

原 sidecar 的 `time` 保留为**已完成记录的逻辑日历回放时间**。它用于把贡献分配给所属小时。整条记录在这个逻辑时刻视为可用；不声称真实流量在原始首包时刻已全部完成，也不依赖尚未核准单位的 `flowDuration` 推算可用时间。

本次不指定原时间的时区，不把一小时当作真实运行必须等待一小时。任务日历、注入墙钟时间、链上完成时间尚未校准。**不能在下一步直接把“原日历一小时”与现有固定 250 TPS 下的墙钟容量混算。**

样例包含 258 个日历小时：`2016-09-22 19:31:32.056236` 至 `2016-10-03 12:19:25.197386`。所以登记任务为 `258 × 7 = 1,806`。其中 1,213 个没有观察到贡献。

样例首小时有 1 个已激活任务被左边界截断，末小时有 6 个被右边界截断；另有 586 个已激活任务覆盖完整小时。末尾没有为了补齐生命周期读取第 100,001 条之后的数据。因此所有任务访问次数均指本样例内观察值。

## 5. 一个由本版生成器实际产生的例子

按冻结排序，G02 的预登记成员恰好是：`TribySpeaker、HelloBarbie、LiFXBulb、TPLinkSmartPlug`。这不是为了让此前示例成立而手工选组。

2016-09-30 的 19:00–20:00，G02 对应任务：

```text
iot-network-activity-collection|20160930T19|G02|credit-account
状态地址：0x96ef589b82f6a03729af9358a1947425e64e88a9
```

在样例中的实际对应关系是：

| 原 tx_index | 原时间 | 原设备与协议 | 旧状态地址 | 新状态 |
|---|---|---|---|---|
| 5683 | 19:30:02.367889 | TPLinkSmartPlug，none | `0xbb30bbc409e3b23960d21a8b60b7bee991c40bb2` | 同一 G02 小时任务账户 S |
| 5710 | 19:30:20.152722 | TPLinkSmartPlug，dns | `0x44f46e77c8a3b0de10015b21f713637652fac68c` | S |
| 5737 | 19:31:06.227634 | TribySpeaker，dns | `0xc7037315ad6e1f1b54ae11644a7747132c5b1c63` | S |

旧状态键分别包含设备、端点、服务端口和协议，例如：

```text
记录 5710：device:tplinksmartplug
          + peer:gateway:192.168.1.1+local:192.168.1.227
          + service:53 + proto:dns

记录 5737：device:tribyspeaker
          + peer:gateway:192.168.1.1
          + service:53 + proto:dns
```

原系统中，插座的 DNS 状态和音箱的 DNS 状态是不同账户。新系统中，它们属于同一轮登记采集任务，因此都从 S 获得积分。共享依据是**构造的任务登记关系**；即使这两条记录不访问同一个 DNS，也仍然归属该任务。

流程如下：

1. 19:00 逻辑日历上登记任务和四人名单；尚无贡献时不算一次放置。
2. 第 5683 条记录到达，任务首次激活。若继续沿用闭合批次处理，则在含该记录的批次中首次选择 S 的分片；后续不再迁移。
3. 第 5710 条成为 `S → TPLinkSmartPlug，1 积分`；第 5737 条成为 `S → TribySpeaker，1 积分`。两条共用 S，不再创建两个状态。
4. 本任务实际有 53 笔：灯泡 28、音箱 15、插座 10；HelloBarbie 没有贡献，仍保留在登记名单中。首次批次含 21 笔，另 32 笔在下一批到达。
5. 20:00 开始新轮次、新任务身份；已有排队贡献应继续完成。本次只生成任务与交易，没有实现排队执行。

以下是基于这 53 笔的**事后阶段手算，不是算法运行结果**：

| 假设 S 放在哪片 | 同片交易 | 跨片交易 | 总处理阶段 |
|---|---:|---:|---:|
| 灯泡所在分片 5 | 28 | 25 | 78 |
| 音箱所在分片 2 | 15 | 38 | 91 |
| 插座所在分片 4 | 10 | 43 | 96 |
| 其他分片 | 0 | 53 | 106 |

每笔在 S 所在片执行一个源阶段，跨片时再加设备片的远端阶段。未来 28/15/10 的份额只存在审计结果里；创建时均匀先验是四个登记成员各 1/4。不能把真实份额提前交给候选、容量规则或 PPO。

## 6. 这次能支持什么，不能支持什么

**已经支持的判断：**同一个状态确实产生了面向不同设备的交易；593 个状态均可提供多分片登记上下文；出现了放置后继续收到交易的情况。这解决了旧样例中“状态绑定报告设备，额外锚点主要是特征”的结构问题。

**仍然存在的限制：**

- 198 个状态仍为单设备访问；395 个共享状态中仍有明显偏斜。没有筛掉这些不利情况。
- 7 个分组固定、任务同步按小时更换，结构较简单，历史频率规则可能已经很强。此次没有刻意加入让 PPO 获利的动态成员变化。
- 任务语义与成员是构造的，尚无外部任务系统或应用日志验证。数据来自原始轨迹，不代表任务本身真实存在。
- 59.58% 的贡献发生在首次批次之后，说明长期成本值得计量，不证明 PPO 比合理的历史估计更好。
- 本次没有服务能力、队列与完成时间结果，不能判断容量感知是否有效。

仅做结构诊断：若允许看完整样例的未来访问、没有任何容量约束，每个状态都放在访问最多的设备分片，则最少跨片为 **25,966 笔（25.966%）**，总阶段为 125,966。这是事后跨片下界，不是可部署算法，也不代表这些放置能满足容量。

分片 2 对应的固定设备合计涉及 26,294 笔交易。无论任务账户怎么放，这些交易都至少在设备分片承担一个相应处理阶段，所以只改变任务放置也消不掉全部热点。

## 8. 下一步具体执行顺序

1. **固定这版作为开发样例，先不改分组来追求更高共享比例。**保留单设备任务、空登记、低活跃设备和样本边界。
2. **做最小时间与执行对账。**选包含上述共享任务的少量事件，核对 Go 的状态→设备身份和本片/跨片阶段；明确逻辑日历怎样映射注入时钟，预算和排队使用同一时间单位。任务注册先验须按创建时间可见。
3. **用同一任务数据比较三种放置规则：Hash、原 Candidate-only（旧容量过滤关）、CAP-now。**只加入当前已知工作和放置后各片新增阶段；当前批次多次放置要更新临时压力。比较跨片、总阶段、最忙片绝对工作和积压，先不加入未来预留或学习。
4. **用开发数据确定并冻结正式采样范围与时钟。**随后再检查更大训练前缀、验证窗口的任务数/共享度和边界；本次没有读取它们，不推算全量状态总数。
5. **只有规则实验确实存在可解释的改进空间，再加入 CAP-reserve 和 PPO。**PPO 前先处理跨批奖励及无新动作批次的成本归因。成员数、时长、编组种子及同步/错峰创建的敏感性检验届时另立版本，保留所有预定场景，不能只汇报有利种子。

本次停止在第 1 步的数据生成与统计，外加 Python 读取兼容性检查；没有提前修改系统源码或启动后续算法实验。
