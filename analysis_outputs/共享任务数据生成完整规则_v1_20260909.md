## 1. 先用通俗的话理解整个规则

把平台理解成一个组织“设备网络活动采集”的任务发布者。平台先给设备分组，每小时让各组开始一轮新任务。每组这一轮共用一本积分账本；组内设备每提交一条记录，就从这本账本得到 1 积分。

在系统中：

| 通俗说法 | 系统中的含义 |
|---|---|
| 参加采集的设备 | 保持原身份和固定归属分片的设备账户 |
| 一组设备的一轮小时任务 | 一个任务实例，有固定成员名单和截止时间 |
| 这轮任务共用的积分账本 | 一个任务状态账户，是首次放置的对象 |
| 设备提交一次贡献并获得积分 | 一笔“任务账户 → 该设备账户”的二账户交易 |
| 给账本选择存放位置 | 为任务状态选择一个分片，后续贡献继续使用该位置 |

**原数据提供的是设备流量记录；设备编组、采集任务和积分机制是我们明确构造的应用假设。**不能把构造出的任务说成从 DNS、云 IP 或真实任务平台中识别出来的业务。

## 3. 设备分组规则

### 3.1 具体怎样分组

1. 固定分组种子为字符串 `20260909`。
2. 对每台登记设备，将种子、一个竖线分隔符和小写设备名拼接，计算 SHA-256。
3. 按摘要从小到大排序；若摘要相同，以设备名排序。
4. 排序后连续每四台组成一组，编号 G01、G02……；最后三台组成 G07，不补设备、不丢设备。
5. 分组在整个样例中保持不变，每小时沿用同一组成员。

这样同一设备名单、同一种子总会得到同一分组。排序过程不读取设备分片、未来流量、原状态访问图、基线分数或 PPO 输出。

### 3.2 为什么先选四台、固定分组

每组四台可以先验证“一个状态对应有限数量的多个设备”，也便于逐笔解释；固定分组避免第一版同时引入成员变化、社区检测和未来访问预测等问题。最后三台完整保留。

**四台不是数据集证明的最优组大小，固定种子也没有经过效果筛选。**这些只是本版公开假设。分组不证明成员属于真实的同一个家庭、工厂或网络，也没有保证组内所有设备都会活跃。

## 4. 小时任务的创建和结束

### 4.1 每组每小时一个独立任务

任务周期和任务寿命均为 3,600 秒。按照原时间字段的字面日历整点划分：

```text
19:00:00 ≤ 记录时间 < 20:00:00 → 19 点这一轮任务
20:00:00 ≤ 记录时间 < 21:00:00 → 20 点这一轮任务
```

所以 19:59:59 属于旧轮次，恰好 20:00:00 属于新轮次。这里按时间划分，不是“每凑够若干条交易就建立一个新状态”。

每个与样本相交的小时都为七个组登记任务，包括整个小时没有贡献的组。空任务保留在登记表中，不能事后只保留有多人贡献的任务。

### 4.2 任务、状态和首次放置不是同一个数量

- **登记任务**：平台计划执行的一轮采集，已经有任务身份、名单和截止时间。
- **激活状态**：该任务已经出现第一条贡献，需要一个实际承接交易的任务账户。
- **首次放置**：为这个首次激活的状态选择分片。每个不同激活状态只需要一次；本轮仅统计应有次数，没有执行放置。

例如一个小时登记七个任务，但只有六个组有贡献，就只有六个新状态需要首次放置。没有贡献的那个任务不是“放置失败”，而是尚未激活。

### 4.3 到了下一小时会发生什么

同一组开始一轮新任务，使用新任务账户；旧任务不再接收按本规则归入新小时的贡献。

这代表预先规定的独立采集轮次，不是将一个运行中的热点账户按负载拆开，也不是把旧账户迁移或删除。后续链上实现中，旧任务已经入队的贡献仍须处理完成，旧账户和余额应保留。本轮未实现这部分执行过程。

如果业务要求一个状态跨多个小时持续更新，那么它属于另一种语义，不能直接套用“一小时新建账户”并声称业务等价。

## 5. 状态身份和地址规则

应用标识固定为 `iot-network-activity-collection`，状态类型固定为 `credit-account`。

任务身份由应用、小时、组和状态类型拼接。例如：

```text
iot-network-activity-collection|20160930T19|G02|credit-account
```

日期小时格式为 `YYYYMMDDTHH`。对应的可读状态键为在任务身份前添加 `iot_task:`。

本版生成器将可读状态键去除首尾空格、转为小写，再以 UTF-8 编码计算 SHA-1，添加 `0x` 前缀得到 40 位十六进制账户地址。上述任务地址为：

```text
0x96ef589b82f6a03729af9358a1947425e64e88a9
```

设备地址沿用原数据身份。固定种子、设备名单和状态编码不变时，扩展样本不会改变已有时刻的任务身份。训练/验证边界也不能仅因切文件就替同一个任务再造一个地址。

16 分片只用于本次描述部署：设备地址最后八位十六进制数对 16 取余，即现有地址分片口径。**得到设备分片后不反过来调整组成员，也不在生成阶段给任务选择分片。**

## 6. 一条原记录怎样变成一条新交易

对每条输入记录顺序执行：

1. 取得原设备身份和时间。
2. 找到该设备的固定组。
3. 将记录时间向下取整到小时，找到“这个小时＋这个组”的任务。
4. 生成或复用该任务的状态地址。
5. 输出一笔从任务账户向该设备支付 1 积分的交易。
6. 保留原索引、时间、协议、原状态与网络字段等来源信息，便于对账。

同组、同小时的不同协议可以归于同一采集任务。DNS、HTTP 或原对端地址不用于决定共享身份。

这一版每条记录只归属该设备当前的一个任务，不复制成多个任务贡献；一条记录只生成一笔交易。也不把整组设备塞进一笔多方原子交易：每笔仍只有一个任务账户和一个实际设备账户。

### 6.1 积分与原交易值的区别

每笔积分值固定为 1。旧数据的交易值可能来自 payload 等换算，本版不继续将它当作积分数，而是保存在 `source_value` 中。

所有任务的名义初始额度统一为 1,000,000,000 积分。该固定数值不由任务未来真实贡献次数计算；它仅用于这版数据契约与额度充足性检查，**没有在链上实际注资或执行余额初始化**。

任务登记和额外结算交易数量本版都设为 0，注册表在链外。因此 100,000 条输入仍对应 100,000 笔输出；若以后增加创建、充值或结算交易，必须另行计数，并验证余额与执行成功率。

### 6.2 CSV 存储方向与实际执行方向

为兼容原 IoT 适配器，输出继续使用 18 列无表头 CSV：

| 字段位置 | 写入内容 |
|---|---|
| 第 4 列，索引 3 | 本条记录的设备地址 |
| 第 5 列，索引 4 | 新任务状态地址 |
| 第 9 列，索引 8 | 1 积分 |

sidecar 中对应为 `from_address=设备`、`to_address=任务状态`。现有 IoT 适配器读取后将实际方向设置为：

```text
Sender    = 任务状态账户
Recipient = 本条记录的设备账户
Value     = 1
```

CSV 列位置是兼容约定，不能跳过 IoT 身份适配后当成反向交易执行。已通过 Python 读取器检查，不代表已经完成 Go 链上验证。

## 7. 登记名单、实际访问者和权重

### 7.1 创建时知道什么

一个任务创建时，公开该组全部成员、创建时间、计划截止时间、任务类型和固定名义额度。成员名单不是通过扫描这个任务的后续记录得到的。

`anchor_addresses` 写入登记成员的设备地址；`anchor_types` 均为 `device`；`anchor_roles` 均为 `registered_participant`。

登记四台时，每台先验权重为 1/4；登记三台时为 1/3，写出时保留足够精度并检查归一化。这些先验写入 `anchor_weights`，表示参与资格的均匀先验，不表示各设备真的贡献了相同比例的交易。

### 7.2 哪些信息不能提前使用

以下只允许出现在生成后的审计统计中：任务最终事件总数、最终实际访问者、未来访问份额、未来阶段变化。

比如登记 A、B、C、D，最终只有 A 和 B 贡献，不能在生成后将名单缩成 A、B，也不能将均匀先验替换为二者最终频率再交给策略。

本版不预填历史频率预测。以后如增加预测，必须只使用决策时已经可见的历史，并让规则与 PPO 使用相同信息。

## 8. 单设备、空任务和未知设备怎样处理

| 情形 | 处理规则 |
|---|---|
| 登记四人，实际只有一人贡献 | 保留四人名单和均匀先验，统计为单实际设备状态；不改为私有回退 |
| 某组某小时没有贡献 | 保留登记元数据，不生成交易，不计激活状态或首次放置 |
| 已登记设备在样本中一直不活跃 | 仍保留在预登记名单，不为它伪造贡献 |
| 未来出现不在登记名单中的设备 | 为其使用独立的私有小时任务，保留记录并计入回退统计 |

私有回退任务沿用“应用＋小时＋设备私有组＋账户类型”的身份结构，名单只有该设备，权重为 1；该设备同小时后续事件复用此账户。

本次样例没有未知设备，私有回退未触发。其规则已写入生成器，但本样例的“回退为零”不是未知设备分支的覆盖验证。

## 9. 时间口径、批次与窗口边界

### 9.1 为什么称为逻辑日历回放

本版使用原 sidecar 的时间字段，按它显示的日期与小时分配任务，不擅自为原数据补时区。整条记录在这个逻辑回放时刻被视为可用。

这不证明真实 flow 的全部信息在原始首包时刻已经可用。本版不依赖 `flowDuration` 推算结束时刻，也不把其未核准单位当作真实在线时钟。

后续必须明确日历时间如何映射到注入与执行时间。若加速回放，应同步解释任务寿命、工作量窗口和服务能力的时间单位；不能把一小时的任务负载直接与现有固定注入速度下的墙钟容量混算。

### 9.2 每 1,000 条是统计批次，不是一个任务

`batch_size_for_statistics=1000` 只用于统计现有批处理结构。第 i 条记录属于批次 `floor(i/1000)`；100,000 条因此有 100 个批次。

一个批次可能包含多个小时的记录，一个小时也可能跨多个批次。首次批次是包含该任务第一条事件的批次；“首次批次之后的交易”指索引位于后续批次的该任务贡献。

这与“第一条事件出现”和“未来放置器具体何时执行动作”要区分。若沿用闭合批次决策，策略可以使用该批已经到达的记录；本轮只完成数据与统计，没有实际执行动作。

### 9.3 样本首尾如何处理

样本是固定的 100,000 条，不为了补齐任务而读取窗口后面的贡献。登记时间可以早于首条样本记录，末轮任务也可能尚未到期就被样本截断。

本样例时间范围为 `2016-09-22 19:31:32.056236` 至 `2016-10-03 12:19:25.197386`，相交小时为 258 个。

- 第一小时有 1 个激活任务的观察被左边界截断。
- 最后一小时有 6 个激活任务的观察被右边界截断。
- 586 个激活任务的日历小时完整落在观察区间内。

因此报告的是“样例内观察到的贡献数”，不能把边界任务的观察值当作完整生命周期总量。扩大样本或以后切分数据时，任务身份仍保持一致。

## 10. 特征与输出文件规则

### 10.1 本版特征处于什么状态

输出中的协议设置为构造交易类型 `task_credit`。未建模的流量、距离、链路字段显式使用零占位，相关通信成本代理为零；登记成员信息和均匀先验正常保留。

原协议、流量、时间和旧状态等保存在 `source_` 前缀字段中，用于追溯。例如 `source_protocol`、`source_state_object_key`、`source_value`。保留来源不等于这些量已经进入有效的策略特征或通信成本模型。

这些零值表示“当前没有建模”，不能解释为真实距离等于零、链路质量等于零或通信免费。本版可用于身份与访问结构检查，尚不是完整 PPO 训练输入或真实通信成本实验数据。

## 11. 实际数据例子：同一任务的插座、音箱和灯泡

G02 在 2016-09-30 19:00～20:00 的登记成员为：音箱 TribySpeaker、玩具 HelloBarbie、灯泡 LiFXBulb、插座 TPLinkSmartPlug。

使用第 5 节给出的任务账户 S。本版已经实际生成以下对应关系：

| 原记录索引 | 时间 | 设备 | 原协议 | 生成的交易 |
|---|---|---|---|---|
| 5683 | 19:30:02.367889 | TPLinkSmartPlug | none | S → 插座，1 积分；本任务首次激活 |
| 5710 | 19:30:20.152722 | TPLinkSmartPlug | dns | S → 插座，1 积分；复用 S |
| 5737 | 19:31:06.227634 | TribySpeaker | dns | S → 音箱，1 积分；复用 S |

旧规则里，第 5710 条对应状态 `0x44f46e77c8a3b0de10015b21f713637652fac68c`，第 5737 条对应另一个状态 `0xc7037315ad6e1f1b54ae11644a7747132c5b1c63`。旧状态身份包含设备及端点/服务/协议信息，因此插座和音箱的状态是分开的。

新规则里，共享依据是二者属于登记的 G02 同一轮任务，即使网络对端或协议不同也可以共享 S；不是因为二者刚好访问相同 DNS。

这一小时实际生成 53 笔贡献：灯泡 28、音箱 15、插座 10，HelloBarbie 为 0。仍然保留四人名单和各 1/4 的创建先验；28/15/10/0 只进入审计统计。本任务只需要一次首次放置。

设备沿用旧分片：灯泡在 5、音箱在 2、插座在 4。事后手算，如果将 S 放在分片 5，28 笔同片、25 笔跨片，总计 78 个处理阶段；放在分片 2，则 15 笔同片、38 笔跨片，总计 91 个阶段。此处没有考虑容量，也没有实际运行策略。

## 12. 本版统计口径与已经得到的结果

统计“共享”时区分三个层次：

1. **登记多设备**：任务名单不止一个设备。
2. **实际多设备**：样例中，确有至少两个不同设备与同一任务账户发生交易。
3. **实际多设备分片**：这些实际设备的固定归属片至少有两个；多设备不一定必然跨多个分片。

本次统计如下：

| 指标 | 实测值 |
|---|---:|
| 输入记录和输出积分交易 | 各 100,000 |
| 登记设备 / 观察到的活跃设备 | 27 / 19 |
| 相交小时 × 每小时组数 | 258 × 7 |
| 登记任务 | 1,806 |
| 未激活任务 | 1,213 |
| 激活状态，即应首次放置次数 | 593 |
| 激活状态中的登记多设备状态 | 593 |
| 实际多设备状态 / 实际多设备分片状态 | 395 / 395 |
| 只有一个实际设备的状态 | 198 |
| 实际共享状态的交易量 | 94,230，占 94.23% |
| 每状态交易数最小 / 中位数 / 最大 | 5 / 101 / 565 |
| 首批实际已有多个设备分片的状态 | 369 |
| 首批之后的交易量 | 59,582 |
| 无新状态的统计批次 | 29 / 100 |
| 私有回退交易 | 0 |

新状态数取决于公开的任务身份和实际贡献，不是先指定一个目标再拼凑。因此 593 是本样例结果，不是预设数量；不能据此线性推算全量新状态数，也不能把 100,000 笔交易说成 100,000 个 PPO 放置动作。

这些数据验证了共享交易结构。容量感知、PPO 增量、链上可执行性和论文效果仍需另做实验。完整实测解读见 [此前的规则与统计报告](E:/project_iot/block-emulator-main-iot/analysis_outputs/共享任务小样例_规则与统计_20260909.md)。

## 13. 固定参数、实现范围与版本管理

`parameters_frozen_before_generation=true`、`no_parameter_search=true` 表示本版参数在本次生成前固定，没有看生成后的共享度或算法结果再修改种子、组成员和小时周期。

“冻结”不表示这些是最优参数或永远不能改。以后比较两台/四台/八台、不同任务寿命、错峰创建等，应另立版本和预定实验矩阵，保留原样例，并避免只报告效果好的配置。

当前生成器是针对本版约定的具体实现，代码中仍有小时周期、组大小等固定条件和检查。**`rules.json` 不是修改任意参数就能自动得到正确新场景的通用配置接口。**调整语义时要同时核对生成器、计数、时间边界、侧边特征和下游读取行为。

本次整理只新增本说明文档，没有修改原规则、生成器、数据或系统源码，也没有新运行实验。容量开关、服务率、CAP-now 和 PPO 决策逻辑不属于这份任务生成规则；它们应读取同一套合法输入后另行比较。
