## 3. 修改内容总览

| 原来的问题或局限 | 当前实现 | 作用与边界 |
|---|---|---|
| 场景均值缺少与候选分片的直接对应关系 | 增加 16 维分片成本关系向量 | 给策略提供“成本较高的已知通信关系位于哪个分片”的信息 |
| 账户 flag 是关联数量阈值代理，语义容易被误认为账户类型 | 当前 v3 删除这一输入列 | 从 219 维变为 218 维；不是删掉所有名字中含 flag 的物联网量 |

| 全局均衡与热点奖励使用折算交易负载 | v3 使用实际执行阶段数量 | 同片一次，跨片两端各一次，避免把折算均衡当成实际执行工作量 |
| 场景成本项缺少跨片动作依赖 | 全局只累计跨片交易成本，局部依据已知对端分片成本惩罚 | 场景成本开始直接区分放置结果；仍是场景代理成本 |
| 每个交易批次末尾设为终止 | v3 在完整训练窗口结束时终止 | 批次之间可以连接后续价值 |

| 全局批次奖励重复分配给每个动作 | 每批全局奖励记一次，局部奖励按动作数取均值 | 减轻新账户数不同造成的奖励次数偏差 |
| 输入维数或机制不匹配时可能混用模型 | 检查维数、布局、特征模式、成本模式等元信息 | 明确拒绝不兼容模型，保护旧模型不被误重置 |
| 离线与链上数值不同难以定位 | 增加同输入一致性检查、历史决策只读重放 | 区分决策实现差异与异步历史反馈差异 |

## 4. 当前状态：218 维

以下为 16 个分片、最近 5 个统计窗口、完整输入模式下的布局。编号从 1 开始；Python 数组下标从 0 开始。

| 维度位置 | 数量 | 内容 |
|---|---:|---|
| 1～80 | 5×16=80 | 最近 5 个窗口、每个分片的执行阶段数量 |
| 81～160 | 5×16=80 | 最近 5 个窗口、每个分片的跨片折算数量 |
| 161～176 | 16 | 当前账户关联方的已知分片分布 p |
| 177～192 | 16 | 各分片已放置账户数量占比 u |
| 193～202 | 10 | 基础物联网场景特征 z |
| 203～218 | 16 | 当前账户按对端分片组织的成本关系向量 w |

总维数：

~~~text
80 + 80 + 16 + 16 + 10 + 16 = 218
~~~

### 4.1 历史数量与两种负载

同片交易在所属分片执行一个阶段；跨片交易在发送方、接收方分片分别执行一个阶段。

跨片折算数量沿用每端 0.5 的口径。因此前两组 80 维的含义不同：第一组是执行阶段数量，第二组是跨片折算数量，第二组不是跨片比例。

历史数量使用对数归一化：

~~~text
normalize(x) = clip(log(1+x) / log(1+4M), 0, 1)
M = max(max_block_size, tx_batch_size)
~~~

当前两项配置均为 1000，因此分母为 log(4001)。

离线历史按交易批次推进；Go 历史按实际提交的分片区块更新。异步链上运行与离线模拟不保证每个决策时刻拥有完全相同的历史。两端函数在相同输入下对齐，不等于两次独立运行的状态轨迹逐项一致。

### 4.2 关联分布与账户占比

- p：按照当前 sender_pos_mode 的关系规则，将已经知道放置位置的关联账户统计到各分片，并归一化。没有已知关系时为全零。
- 当前默认 sender_pos_mode=1，使用接收方关联发送方的规则，并保留现有回退关系处理。
- u：各分片已放置账户数量除以全部已放置账户数量。它反映账户放置分布，**不是交易执行阶段负载**。

### 4.3 十维基础物联网特征

| 全局位置 | 特征 | 当前含义 |
|---|---|---|
| 193 | 关联数量 | 当前批次不同通信对端数量，除以 4 后截断到 1 |
| 194 | 平均距离 | 归一化距离的均值 |
| 195 | 最小距离 | 当前批次相关场景的最小归一化距离 |
| 196 | 平均链路质量 | 当前账户视角的有向链路质量均值 |
| 197 | 通信强度代理 | 由场景负载量、持续时间计算并归一化的强度特征 |
| 198 | 设备对端占比 | device 类型所占比例 |
| 199 | 边缘对端占比 | gateway、local/private 等边缘类型占比 |
| 200 | 云对端占比 | cloud 类型占比 |
| 201 | 服务对端占比 | service 类型占比 |
| 202 | 控制协议占比 | 由场景协议及标记规则识别的控制通信比例 |

这些量在当前可见交易批次中聚合，不读取整个数据集的未来账户统计作为决策输入。

当前 data_iot_v2 接入约定要求两端都是逻辑设备账户，因此四类角色占比在现有数据中为 [1,0,0,0]。这些角色维度目前仍保留，不能声称它们在这批数据中提供了有效区分信息。

flowDuration 的物理单位尚未确认，因此第 197 维不能直接解释为已验证的真实字节/秒。

### 4.4 新增的 16 维成本关系

设当前账户为 u，当前批次中 u 与对端 v 关联的原始交易场景成本之和为 C(u,v)。对端 v 已放置在分片 s 时，该成本才计入 s 的分子。

~~~text
w_s = 已知位于分片 s 的对端关联成本之和 / 当前批次全部非自身对端关联成本之和
~~~

同一笔交易的正向场景成本用于其两端的成本关系构造。该向量按双向账户关联聚合，但不会把同一原始交易的最终全局成本重复计算两次。

未放置对端的成本在分母中、未进入任何已知分片的分子，因此 sum(w_s) 可以小于 1。分母为零时，整组取零。自身交易不作为非自身对端关系加入该向量。

### 4.5 删除的是哪个 flag

删除的是以前位于第 177 维的账户关联度代理：

~~~text
address_flag = 1，当相关账户数量 >= 4
address_flag = 0，其他情况
~~~

它不是通过真实链上账户类型字段获得的“合约账户/普通账户”标志。

该量与其他关联特征的统计口径不完全相同，不能严格声称它是重复特征或对模型影响必定为零。此次删除属于明确的输入简化，需要重新训练验证效果。

**第 202 维控制协议占比仍然保留。** 它与被删除的账户代理标记是两个不同的量。

## 5. 动作、转移与终止规则

### 5.1 动作

动作仍为把首次出现的账户放到 16 个分片中的一个，编号为 0～15。

- 已放置账户再次出现时，使用已有位置，不生成迁移动作。
- 默认候选数量为 7，容量保护开关为 0。
- PPO 训练采样动作；冻结评估使用确定性动作。
- 不将回访交易改成额外的账户放置动作。

当前候选评分仍主要依靠关联分布和负载：

~~~text
score_s = 1000*p_s - candidate_load_weight*pressure_s
          + 0.001*I(s 为账户哈希分片)

pressure_s = 1000*u_s + 最近历史窗口执行阶段数量的均值
~~~

默认 candidate_load_weight=1。该评分不直接加入物联网场景成本向量。

candidate_only（仅候选评分）直接按候选规则选分片；PPO 在允许的候选范围内由网络选分片。因此两者共享一部分关系和负载机制，比较时应识别这部分共同贡献。

### 5.2 状态转移

当前默认处理顺序为：

1. 读取当前交易批次及其场景。
2. 聚合当前可见的账户关系和场景信息。
3. 先处理发送方，再处理接收方；只有新账户产生动作。
4. 每次放置立即更新账户位置和账户数量，后续动作能看到已完成的放置。
5. 按真实发送方、接收方位置计算同片或跨片执行阶段。
6. 更新历史统计，推进到下一交易批次。

环境内部还保存完整账户映射、数据位置等信息。218 维是提供给策略的压缩观测；**不能仅凭这个维度就认为已经证明严格的马尔可夫充分性**。

### 5.3 终止与更新

旧离线流程把每个交易批次的最后一个动作设为 done=True。当前 v3 不再把普通批次边界当作终止：

- 同一训练窗口内连续连接批次。
- 常规更新需同时达到至少 1024 个动作及至少 8 个完整批次，并等到下一次真实决策状态出现。
- 更新时使用下一状态的价值估计，再采样更新后策略的新动作。
- 完整训练窗口结束时才设真实终止，并刷新剩余样本。
- 下一训练轮重新初始化账户放置和历史，不跨训练轮承接旧放置。

这解决了“每批必定截断”的问题，但有限采样片段仍使用价值估计。不能据此声称所有未来交易收益都已经精确归因给任意久以前的首次放置动作。

## 6. 当前奖励与回报计算

以下公式对应 full + cross、默认权重。clip(x,a,b) 表示将 x 截断到 [a,b]；I 表示条件成立取 1，否则取 0。

### 6.1 单笔场景成本

令 d_i 为场景距离，Q_i 为正向链路质量，B_i 为双向有效负载字节数之和：

~~~text
c_i = clip(d_i/60, 0, 1)
      * (1-Q_i)
      * max(0.05, clip(log(1+B_i)/log(1+1000000), 0, 1))
~~~

该值综合距离、链路质量和通信负载。它是构造场景中的无量纲代理成本，不是实测能耗、网络时延或网络传输总字节。

### 6.2 局部动作奖励

令 a 为所选分片；p_a 为该分片关联质量；有已知关联时 e_a=1-p_a，否则 e_a=0；rho_a 为该分片放置前账户数与平均账户数之比。

~~~text
r_local = 1.4*p_a - 0.8*e_a - 0.45*sum(w_s, s != a) + U(rho_a)

当 rho_a <= 1：
U = 0.10*(1-rho_a) + min(0.18, 0.25*(1-rho_a))

当 rho_a > 1：
U = -0.55*(rho_a-1) - 0.35*max(rho_a-1.5, 0)
~~~

平均账户数为零时，不计算上述账户负载项。

局部奖励没有被删除。v3 把局部通信惩罚改为“放置后落在其他分片的已知关联成本份额”。局部负载项仍约束账户数量，全局均衡项则约束执行阶段数量，两者含义不同。

### 6.3 全局批次奖励

对于含 N 笔原始交易的批次：

~~~text
X = 跨片原始交易数 / N
C = sum(c_i * I(交易 i 跨片)) / N

R_batch = 0.55*(1-X) + 0.30*W - 0.10*C - 0.05*H
~~~

L_s 为分片 s 的执行阶段数量，mu 为 16 个分片的平均阶段数量，epsilon=1e-8：

~~~text
V = Var(L) / (mu^2 + epsilon)
D = sum(abs(L_s-mu)) / (mu + epsilon)
W = exp(-0.1*D) / (1+V)

h = max(L_s) / (sum(L_s)+epsilon)
H = clip((h-0.45)/(1-0.45+epsilon), 0, 1)
~~~

v3 的主要口径变化在于 W、H 使用执行阶段负载。同片贡献一个阶段，跨片贡献两个阶段，不能再把跨片两端各 0.5 的折算值当作均衡项的执行工作量。

跨片原始交易的场景成本只记一次；Go 不在第二个中继阶段重复计价。

### 6.4 分配给 PPO 的动作奖励

一个批次有 m 个新放置动作时，第 j 个动作得到：

~~~text
r_j = 0.1 * [
    0.65/m * clip(r_local,j, -1, 1)
    + 0.35 * I(j 为本批最后一个动作) * clip(R_batch, -1, 1)
]
~~~

含义：

- 本批局部奖励贡献按动作数平均。
- 本批全局奖励只加入一次。
- 不是把同一个全局奖励复制 m 次。
- 没有新动作的纯回访批次，其全局奖励按经过的批次数折扣后加入此前待完成转移。

当前训练入口的有效局部权重使用 max(0.65, local_reward_weight)。本轮命令显式设置 0.65。配置文件中旧字段默认值为 0，并不意味着当前 v3 实际没有局部奖励。

### 6.5 折扣与优势估计

默认 gamma=0.99，GAE 的 lambda=0.95，折扣时钟为交易批次：

- 同批动作之间不推进执行时钟，转移折扣和优势递推系数为 1。
- 跨越 Delta 个批次，价值折扣为 gamma^Delta，优势递推系数为 (gamma*lambda)^Delta。
- 完整窗口终止时后续价值归零。
- 中间更新边界使用下一次真实决策状态估计后续价值，不伪装成窗口终止。

同一数值的 gamma，在“每动作折扣”和“每批次折扣”中不是同一个时间尺度，因此不能只看参数值未变就认为长期回报设置没有变化。

## 7. 消融开关及可回答的问题

| 组合 | 网络输入 | 场景成本奖励 | 可回答的问题 |
|---|---|---|---|
| full + cross | 保留场景和分片成本关系输入 | 保留 | 完整方案表现 |
| no_iot + cross | 基础场景 z 的后 9 维和新增 16 维成本输入置零；保留关联数量 | 保留 | 物联网输入是否有增益 |
| full + off | 保留完整输入 | 局部、全局场景成本惩罚关闭 | 场景成本奖励是否有增益 |
| no_iot + off | 屏蔽场景输入 | 关闭 | 同时移除这两类物联网因素的对照 |

所有组合维数都保持 218，避免同时改变网络输入层规模。评估指标仍根据真实场景计算，不因屏蔽输入或关闭成本奖励而关闭指标。

no_iot + cross 仍通过奖励感知场景成本，不能叫“完全不考虑物联网”。不同组合必须分别训练，并在评估、链上准备时使用匹配的开关，不应靠跳过兼容性检查混用模型。

## 8. 两端对齐、模型保护和运行方式

1. Python、Go 都构造当前 218 维状态，包括删除账户标记及追加成本关系输入。
2. 两端使用一致的特征屏蔽、局部成本惩罚、全局成本计数和阶段负载奖励口径。
3. 一致性脚本比较交易、状态、动作掩码、局部及全局奖励；带模型时，还检查真实 Go 到 Python 的推理调用。
4. 历史重放工具读取已经记录的状态、掩码和模型，检查相同输入下是否得到相同决策。它不重写原结果。
5. 模型元信息包含机制、布局、奖励负载口径、轨迹版本、输入模式与成本模式。
6. 当前正式 v3 入口不接受 203 或 219 维模型冒充 218 维模型。需重新训练当前模型。
7. 显式携带历史布局信息的冻结重放可读取旧 219 维模型；这不等于旧模型能直接用于当前新布局。
8. v3 推理失败、结果缺失或非法动作会报错停止，不能静默换成其他规则后继续声称是 PPO。
9. 旧在线更新和旧批量调试入口会拒绝误用 v3 模型，避免把维度不同误认为模型损坏后重置。
10. 运行准备工具共享指定程序、模型和 Python 源码，并保存摘要校验。源码或程序变化后，应重新准备新的运行目录。
11. 根目录旧 bat 入口要求显式传入 legacy。新实验使用相应运行目录的 run.ps1。

## 9. 评估指标与模型选择

训练奖励和评估指标相关，但分母并不完全相同：

| 指标 | 计算 | 用途 |
|---|---|---|
| 普通跨片率 | sum(I_cross)/N | 普通交易跨片程度 |
| 成本加权跨片率 | sum(c_i*I_cross)/sum(c_i) | 场景成本有多大比例落在跨片交易上 |
| 字节加权跨片率 | sum(B_i*I_cross)/sum(B_i) | 场景负载字节有多大比例落在跨片交易上 |
| 每笔跨片场景成本 | sum(c_i*I_cross)/N | 对应全局奖励中的成本口径 |
| 阶段负载归一化方差 | Var(L)/mean(L)^2 | 执行负载不均衡程度 |
| 阶段负载 Jain 公平指数 | (sum(L))^2 / (16*sum(L_s^2)) | 分片执行负载公平性 |
| 最大阶段负载占比 | max(L)/sum(L) | 热点集中程度 |
| 执行阶段放大倍数 | sum(L)/N | 额外执行工作量；完整计数时为 1+普通跨片率 |
| 平均、95 分位确认时延 | 已确认交易时延的均值、95 分位数 | 真实链上确认表现 |

零分母指标不能擅自解释为零成本或完美公平，应遵循分析输出的空值处理。字节来自场景负载字段，不等于测量到的网络协议开销。离线放置评估不产生真实链上确认时延。

分析中分别保留阶段负载与折算负载。链上完整窗口的阶段统计应看 iot_metrics.execution_load，不能把旧 period 表中的折算方差直接当作阶段方差。

高成本、大负载、长距离、弱链路等分组阈值由统一参考窗口确定；本轮使用验证集的 5 万笔。分组可以重叠，不能简单相加当作互斥分类。

本轮训练命令使用训练入口按照固定验证集综合评分保存的 ppo_best.pt，不使用测试结果挑选模型。代码也保留独立的 Pareto 筛选入口，v3 分支考虑成本目标及阶段负载约束；本轮给出的命令未额外调用该入口。

**机制修正和指标补充不保证 PPO 必然优于候选规则。** 应同时比较完整输入模型、屏蔽输入模型和规则基线，识别输入收益、学习收益及不同指标之间的取舍。

## 12. 正式数据划分与 1 万笔验收的区别

**原先的 20 万训练、5 万验证、最后 5 万正式评估方案没有取消，也不应改成只用 1 万笔正式评估。**

程序窗口参数使用从 0 开始的索引；以下同时列出日常“第几笔”的编号。

| 用途 | 第几笔交易 | 从 0 开始的区间，右端不含 | start 参数 | 数量 |
|---|---|---|---:|---:|
| 训练 | 1～200000 | [0,200000) | 0 | 200000 |
| 验证及选模型 | 200001～250000 | [200000,250000) | 200000 | 50000 |
| 正式离线测试 | 250001～300000 | [250000,300000) | 250000 | 50000 |
| 正式 BlockEmulator 链上评估 | 250001～300000 | [250000,300000) | 250000 | 50000 |
| 可选的链上功能验收 | 250001～260000 | [250000,260000) | 250000 | 10000 |

### 12.1 上次命令并不是“数据集最后一万笔”

上次链上验收参数为 start-tx=250000、max-txs=10000，取的是**最后 5 万测试窗口中的前 1 万笔**。

如果取整个数据集的最后 1 万，应是 [290000,300000)，但这不是上次给出的参数。

### 12.2 1 万笔是否太少

- 用于验证新模型能加载、两端能通信、交易能完整确认、指标能完整关联，1 万笔可以作为工程验收窗口。
- 用于正式报告完整测试集上的策略优劣，1 万笔不能替代约定的最后 5 万笔。
- 短窗口的首次放置比例、账户复用程度、冷启动占比和场景分布可能不同；250 笔/秒下注入 1 万笔的名义时间仅 40 秒，启动、排队和收尾效应也可能更突出。
- 即使使用完整 5 万笔，也只是当前数据集的完整测试窗口，不自动等于已经证明跨数据规模、跨种子的普遍结论。

### 12.3 当前建议的完整推进顺序

1. 在前 20 万笔上分别训练 full 和 no_iot 模型，均用中间 5 万笔选模型。
2. 在最后 5 万笔上完成 hash、heuristic、candidate_only、ppo_full、ppo_no_iot 的离线对照。
3. 检查两个新模型的 Go/Python 接口和版本；按需先做 1 万笔工程验收。
4. **正式 BlockEmulator 评估使用完整最后 5 万笔**。原来的四组主对照为 hash、heuristic、candidate_only、ppo_full；验证输入作用时增加 ppo_no_iot。
5. 第一轮正式链上对照统一为 250 笔/秒、相同程序版本、相同模型选择规则与种子。随后在相同完整窗口下做 500 笔/秒及多种子等扩展。

1 万笔验收是可选的工程步骤，不是新的数据划分。若模型接口检查通过，也可以直接开展完整 5 万笔链上运行，并同时检查其完整性。

如果已经做过 1 万笔，正式 5 万笔应在新运行目录中从 start-tx=250000 重新运行。不要把先跑的 1 万与另一次冷启动的 4 万结果拼接成一次连续 5 万实验。

各策略必须使用相同的 5 万笔窗口和初始化规则，等待交易完成确认后比较指标。不能把某策略的 1 万笔结果与另一策略的 5 万笔结果直接并列作为正式结论。测试结果不用于反向挑选训练轮次；持续根据这批测试反馈修改系统时，应将其视为已观察基准，最终泛化结论还需独立数据或窗口。
