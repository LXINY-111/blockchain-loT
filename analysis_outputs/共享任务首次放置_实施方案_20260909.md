## 2. 共享任务数据是否需要重新处理、生成

**需要生成一份新的派生交易数据和配套特征，不能仅改文件名、训练参数或给旧特征增加几个锚点。原始 IoT 数据不需要重新下载或覆盖。**

现有生成器把报告设备放进状态标识，常见结构近似为：

```text
旧状态标识 = 设备 + 对端/服务信息 + 端口/协议
设备 A 的状态 S_A 与设备 B 的状态 S_B 是两个账户
```

共享任务则采用：

```text
新状态标识 = 应用/租户标识 + 任务实例标识 + 状态类型
参与同一任务的 A、B、C 对应同一个状态 S
```

新数据至少改变 state ID、逐条交易的设备与状态对应关系、参与设备上下文和任务元数据。锚点集合、统计摘要、数据散列也需要重新生成；不能沿用旧模型旁边的旧 sidecar。

| 内容 | 处理办法 |
|---|---|
| 原始 flow 文件、现有 CSV/sidecar、旧实验结果 | 保留，只读使用 |
| CSV 格式、账户地址编码和数据加载框架 | 优先复用 |
| 设备活动频率、突发性、事件顺序 | 可以用现有数据校准或驱动；校准来源单独记录 |
| 任务、任务参与者、生命周期、积分交易 | 新构造，明确声明为应用模型 |
| 原有 DNS/云 IP 锚点、primary owner 语义 | 不直接当作共享任务参与者；需替换或降为原始来源字段 |
| 距离、链路质量、通信权重 | 重新确认含义；第一阶段可禁用无明确成本对应的部分 |
| PPO 权重 | 新数据/奖励/特征语义下重新训练；保留架构不等于直接复用旧权重 |

不要反复扫描 3.68 GB 的旧 sidecar 来调生成参数。后续实现时可以先只从约定的校准前缀提取必要统计，再按冻结的配置生成工作负载。这个统计文件属于以后实现的输入，不在本次文档整理中创建。

## 3. 选择与当前执行方向兼容的应用语义

### 3.1 建议使用“协作任务积分账户”

一个协作采集任务有一个预置额度的积分账户。参与设备完成一次贡献，由任务账户向该设备账户转移一单位积分。状态是任务的账本账户；设备是多个交易对手。

这与当前 Go 和 Python 中的执行方向兼容：

```text
实际 Sender    = 状态对象账户
实际 Recipient = 本条事件对应的设备锚点账户
实际 Value     = 固定一单位，或预先声明的积分规则
```

当前代码依据：

- [Go 交易身份改写](E:/project_iot/block-emulator-main-iot/supervisor/committee/spring_iot.go:226)：Sender 为 StateObject，Recipient 为 AnchorObject。
- [Python 加载及离线执行](E:/project_iot/block-emulator-main-iot/spring_lite/offline_env.py)：同样用状态作为 sender、设备作为 recipient。
- [旧数据生成器](E:/project_iot/block-emulator-main-iot/spring_lite/prepare_iot_multi_anchor_dataset.py:541)：旧 state key 包含设备信息。

**“任务积分账户”是为复用现有执行方式提出的应用抽象，不是从原始流量中识别出来的真实积分系统。**原始一条 flow 变成一条积分事件属于构造规则。链上只实现账户转移和放置，不声称已实现任务验真、奖励合约或真实资金结算。

已有执行器会为缺失账户使用初始余额。实现时应明确固定初始化预算、整数积分单位、唯一交易 ID 和余额检查；预算不作为向策略暴露未来总交易量的通道。不能让余额不足导致交易未执行，却仍被统计为成功。

### 3.2 与此前 D3 的区别

| 项目 | 现有 v1 | 此前 D3 诊断 | 本方案共享任务 |
|---|---|---|---|
| 状态依据 | 设备及网络端点信息 | 当前记录唯一服务端点；歧义时私有回退 | 应用、任务实例、状态类型 |
| 共享如何产生 | 很多是上下文锚点；执行设备通常固定 | 不同报告设备映射到同一服务对象 | 多个参与设备确实与同一任务账户交易 |
| 首次放置时的信息 | 当前批次及旧特征 | 当前批次，未来参与者可能很晚才出现 | 创建时登记名单＋当时已到达事件＋合法历史 |
| 执行方向 | 状态 → 设备 | 先前方案讨论过设备 → 状态计数 | 状态 → 设备，优先保持现有方向 |
| 本轮定位 | 历史结果对照 | 补充诊断与后续验证 | 优先开展的小规模主线验证 |

D3 的 4,754 个状态不是新任务数据的固定数量要求。改成任务积分语义后，必须重新计算成本、热点和效果；不能把 D3 的跨片率直接用作本方案结果。交易方向改变时，有向网络开销也不能沿用。

## 4. 一条完整的放置和执行示例

以下数字全部是手算示例。

1. 任务 T001 创建，公布参与设备 A、B、C；设备固定归属分片 2、5、9。
2. 为 T001 生成唯一状态账户 S001。系统只知道名单、任务类型及历史估计，不知道未来准确贡献次数。
3. 第一条事件到达；按现有已闭合批次触发首次放置，不再额外等几个批次。批次内只能使用已经到达的记录。
4. 候选模块得到参与关系及容量压力；容量规则或 PPO 选择 S001 所在分片，例如分片 5。
5. 保存 S001 → 5。之后所有算法都不再为 S001 重新选片；同批后续新任务应看到已经增加的预计压力。
6. 回放 S001→A、S001→B、S001→A、S001→C 四笔交易。
7. S001→B 是本片交易，其余三笔是跨片交易。分片 5 执行四个源阶段，分片 2 执行两个远端阶段，分片 9 执行一个远端阶段，共七个阶段。
8. 交易到达、排队和完成时更新账本及容量估计。任务结束后释放未来工作量预留，账户及余额仍保留；不要把释放预留等同于删除状态。
9. 新任务 T002 创建新状态 S002，再进行一次首次放置。旧任务跨过训练/评估边界时保持原身份。

这个例子是“多笔二账户交易共享一个状态”，不要求“一笔交易同时原子更新多个设备账户”。后一种需求会涉及额外执行协议，不属于最小实现。

## 5. 数据生成契约与防止信息泄漏

### 5.1 建议的两级工作负载

**先做可控任务仿真。**固定设备集合和部署映射，按公开配置生成任务创建、参与集合、生命周期及贡献事件。用它核对算法、阶段计数和容量冲突；其中没有依据原始数据校准的参数必须标成假设。

**再做真实轨迹驱动的任务增强。**保留旧数据的报告设备和记录回放顺序，把事件按冻结的应用规则分配给该设备当前参与的任务。可以保留全部事件，并对没有合适共享任务的事件使用明确的私有任务回退；统计回退比例，不删掉不利事件。

两级分别命名和报告，不能把全仿真称为真实数据，也不能把不同数据定义下的算法数值直接相减当作算法收益。真实流量校准的活动统计，不自动证明构造的任务共享关系真实存在。

### 5.2 一个可实现的因果生成流程

1. 预先声明应用域和设备成员。可按部署假设或固定随机种子生成，不能根据评估全量访问图事后聚类后当作在线先验。
2. 按冻结的任务到达规律创建任务，给定创建时可公布的参与名单、类型和计划截止时间。
3. 贡献事件只由当前已存在任务产生；轨迹增强时，只能把设备事件分给包含它的当前任务。分配只用当时信息。
4. 名单表示获准参与，并不保证每个设备最终都有事件。额外统计“登记共享”与“实际共享”；不能扫描未来后只保留确实共享的任务。
5. 实际持续时间、贡献次数、成员权重可以随机变化；实现固定、可解释的规律，并纳入不可预测和对称场景。
6. 任务到期后停止为其生成新贡献，已进入执行队列的交易继续完成。已到达但未完成的贡献不能丢失。
7. 固定种子后导出交易、sidecar、任务元数据、设备归属与 manifest，再由所有方法读取同一份输入。

若每个任务都连接所有分片且访问完全均匀，亲和放置可能没有优势；若访问变化完全独立随机，PPO也无法可靠预测。要覆盖这些边界，不能只保留有利情形。

### 5.3 文件和字段约定（拟实现）

| 产物 | 核心内容 | 使用规则 |
|---|---|---|
| 交易 CSV | 保持现有 18 列无表头 CSV 的字段位置及辅助列；提供兼容地址与积分值 | 不直接把第 4/5 列方向当作 IoT 适配后的最终执行方向 |
| sidecar | tx_index、from_address、to_address、参与设备及合法特征 | 与 CSV 一一对应，编号/顺序无缺失重复 |
| 任务注册表 | task_id、application_id、state_address、created_at、participants、task_type、公开截止时间 | 决策时只可读取 created_at 不晚于当前的元数据 |
| 生成审计表 | 实际终止时刻、未来事件总数、真实访问分布 | 仅评估使用，不进入观测或候选生成 |
| 部署表 | 设备 → 固定分片；可选网关/拓扑 | 各算法一致，评估前冻结 |
| manifest | schema/生成器版本、所有种子、单位、数据来源、参数、分割、散列 | 用于复现与身份核对 |

为了兼容现有 IoT 适配器，sidecar 暂保留：`from_address=本条设备账户`、`to_address=任务状态账户`；适配后的链上执行仍为“任务状态 → 设备”。必须以逐笔夹具验证这种改写，不能在一个基线中漏开身份模式而反向执行。

`anchor_addresses` 可承载创建时已公布的参与名单；`anchor_weights` 第一版可使用名单均匀先验，之后才比较由过去同类任务得到的估计。不能填写该任务未来真实频次。读取程序对列表、归一化、当前交易实际设备是否属于名单都要校验。

建议增加可区分的观测来源：实际已到达交易频次、注册名单先验、过去任务统计。名单重复出现在多条 sidecar 中时，不应被错误解释为各成员都发生了对应次数的实际交易。

原始 flow 的首包时间、记录可用时间和实验回放时间必须区分。旧数据的时长单位尚有待核验，第一版不依赖它推导真实在线可用时刻；使用明确的已完成记录回放时钟。原始 payload 不直接等于积分交易或 Relay 消息字节。

### 5.4 首次决策与评估覆盖

每个数据窗口都同时报告：新状态数、实际多设备状态数、实际跨多个设备分片的状态数、首次决策时可见多成员状态数、只观察到单设备的状态数、后续访问量、无新决策批次比例、退化回退比例。

增加任务数必须来自公开的任务生命周期和创建规律，不是为了凑训练步数随意切时间桶。重复 epoch 不增加独立任务/环境样本。旧 D3 的 6,209 次来自分窗冷启动口径，不能写成 6,209 个不重复状态。

## 6. 容量感知规则：现在有什么、需要补什么

### 6.1 现有 Candidate-only 已经考虑负载

当前 Python `_candidate_scores` 与 Go `springCandidateScores` 的核心是：

```text
得分 = 1000 × 关联得分 − 负载权重 × 当前压力 + 很小的 Hash 平局偏好
当前压力 = 按分片状态数量占比缩放的压力 + 最近五窗口实际阶段数均值
可选过滤 = 当前压力不超过全片平均压力 × capacity_guard_factor
```

随后保留 Top-K；Candidate-only 选择其中最高分，PPO 从允许动作中选片。

代码依据：[Go 候选实现](E:/project_iot/block-emulator-main-iot/supervisor/committee/spring_candidate.go:45)、[Python 候选实现](E:/project_iot/block-emulator-main-iot/spring_lite/offline_env.py:1275)。

它是有负载感知的启发式，但当前平均值阈值不是实测处理上限，状态数量也不等于执行工作量。它没有明确计算“这个任务放进去后，各片需要增加多少阶段”，也未为活跃任务后续贡献维护逐任务的预留。因此，不把容量感知说成从零增加，而是收紧现有定义。

### 6.2 容量使用什么单位

第一版统一使用“处理阶段数”：本片交易一个阶段；跨片交易源片、目标片各一个阶段。同一逻辑阶段不按 PBFT 副本数重复算成多个交易阶段；副本资源开销另计。

- `H`：容量判断的时间窗口，单位秒。
- `mu[j]`：分片 j 的服务能力估计，单位 stage/s。
- `C[j] = mu[j] × H`：该窗口可以服务的阶段预算。
- `Q[j]`：已知未完成的阶段工作量。
- `R[j]`：预计在未来 H 内到达、尚未计入 Q 的其他工作量。
- `Delta[j,k,a]`：把新任务 k 放到 a 后，预计新增到分片 j 的阶段数。

`mu` 需要明确来源。`BlockSize / BlockInterval` 只提供理想服务上限；例如 1000/5=200 stage/s 不能直接称为已测容量。正式容量评价需独立校准实际服务率，算法间使用相同结果；不能从评估未来表现反推容量。

第一版离线模拟可以先使用声明的服务模型，但必须标明模拟值，后续对齐 Go 的实际时钟和阶段提交。现有“一输入批次消耗一次固定块容量”的模拟方式，不能不经核验就视为真实时间队列。

### 6.3 新任务会增加哪些分片的压力

设任务预计未来 H 内产生 `N` 笔交易；参与设备 i 的预计份额为 `p[i]`，设备固定归属 `h[i]`，份额合计为 1。

```text
Delta[j,k,a] = N × ( I[j=a] + I[j≠a] × sum(p[i] : h[i]=j) )
预计跨片交易数 = N × (1 − sum(p[i] : h[i]=a))
放置后压力 u[j,a] = (Q[j] + R[j] + Delta[j,k,a]) / C[j]
```

含义：每笔交易都在任务所在片执行一个源阶段；设备所在片不同，才追加远端阶段。不能只计算候选片新增工作而漏掉远端设备片。

`N` 和 `p` 必须来自当时可见信息或过去数据；不能来自该任务完整生命周期。若只评价当前已到达的若干事件，可以直接用逐设备已到达计数代替 `N×p`，此时当前阶段需求是确定的。

### 6.4 建议分两级实现

| 规则 | 怎么做 | 目的 |
|---|---|---|
| CAP-now：放置后容量规则 | 用当前已知队列和已到达事件计算放置后的阶段压力；在可接受的分片中按相同亲和/成本信息选择 | 第一阶段的强基线，先让容量单位和动作后果正确 |
| CAP-reserve：任务容量预留 | 在 CAP-now 基础上估计活跃任务未来 H 内尚未到达的工作 R，以及新任务的未来 Delta；维护、更新、释放预留 | 后续机制候选，检查只看当前负载是否低估未来拥堵 |

CAP-now 同一批中的多次放置也要更新临时工作量账本，不能每次都使用批次开始时的空闲值。CAP-reserve 则把这种预计工作维护到任务后续活跃期；不是一次性占满整个生命周期，也不把状态存储大小当处理阶段。

第一版 CAP-reserve 可以按任务类型使用校准前缀中的平均速率/经验分位数，参与份额采用注册名单均匀先验。先不加复杂预测器；如果预测无用，就保留为负结果。按“已完成任务”训练统计时需注意长任务尚未结束的选择偏差。

### 6.5 选择与回退规则

1. 对全部分片计算放置后压力，先得到容量可接受集合，再做 Top-K，避免先剪掉唯一能承接工作的分片。
2. 第一版允许阈值 `theta=1` 表示不超过所声明的窗口预算；若需安全余量，只能在开发/验证集设定并冻结。
3. 在可接受集合里，优先减少预计跨片开销；平局优先降低最大压力，再用稳定地址哈希顺序决定。
4. 若所有分片都超过预算，仍须给出一致、可记录的回退：最小化最大压力，其次最小化归一化超额总量，再比较跨片开销。
5. 回退事件必须计入过载比例、队列、延迟和失败边界。第一版不悄悄丢弃任务，也不额外引入等待队列来隐藏过载。

预测存在误差时，这是一种容量风险控制规则，不是“永不超载”的硬保证。当前系统的全零 mask 自动重新开放全部动作行为，也必须与上述显式回退和记录一致。

### 6.6 一个具体算例

假定三个相关分片在同一窗口的容量均为 1000 stage。已有队列与预留合计为：分片 2 为 850、分片 5 为 400、分片 9 为 200。任务预计 200 笔，设备份额分别为 60%、30%、10%。这些是假设值。

| 放置位置 | 分片 2 放置后工作量 | 分片 5 放置后工作量 | 分片 9 放置后工作量 | 预计跨片数 | 结果 |
|---|---:|---:|---:|---:|---|
| 分片 2 | 1050 | 460 | 220 | 80 | 分片 2 超预算 |
| 分片 5 | 970 | 600 | 220 | 140 | 可接受 |
| 分片 9 | 970 | 460 | 400 | 180 | 可接受 |

仅看亲和关系会选分片 2；容量规则选分片 5，接受更多跨片来避免预计过载。这就是要验证的真实权衡。该例并不保证跨片率和吞吐同时变好。

### 6.7 预留如何更新，避免重复计算

未来工作进入队列时，从未来预留中转为已知待处理工作；阶段提交后从待处理工作扣除。定期根据已观察的任务年龄、活动和剩余公开期限重估未来 H 的需求，任务关闭后释放未来预留，但保留未完成阶段。

源阶段完成而 Relay2 尚未入目标队列的工作仍需记账。应明确区分未到达事件、已收到待源执行、待远端执行、已完成；同一阶段只能处在一种状态。不能同时把同一任务未来量加入逐任务预留和“最近速率 × H”两次。

## 7. 热点与通信问题怎样处理

### 7.1 能解决和不能解决的热点

容量规则可缓解多个任务因亲和关系集中到同一片的问题。容量预留还可提前反映活跃任务的后续工作。

但一个不可拆分任务自身的源阶段速率超过单片能力时，首次放置不能消除它；固定设备片的最低必要工作也不能靠任务换片完全消除。任务粒度应由业务生命周期预先确定，各算法一致，不得看完结果再给主方法专门拆分热点。

真实轨迹中的 27 个设备及活动偏斜继续保留为一个场景。更多虚拟设备或均衡部署属于另一个声明的仿真场景，不能宣称是原始数据规模自然扩大。

### 7.2 第一阶段的成本与最终通信评价

第一阶段先使用能与执行对应的跨片交易数、总阶段数、最大分片工作量、队列等指标。不要继续用一个与动作无关的全局输入权重均值表示优化后的通信开销。

当前 Go 某通信权重把 payload、packets、duration 相加，而 Python 对应计算不同；二者量纲与实现都需统一。局部奖励中有动作相关的跨片项，所以也不能把旧奖励说成完全不受动作影响。

若论文要主张通信成本收益，后续必须统计实际应用层 Relay 消息字节，明确编码头、转发次数、消息类型和失败发送计数。所有网络成本若包含 PBFT、控制或重试消息，应分项统计；只测 Relay 就写 Relay 开销。

距离/链路质量若没有进入实际执行或声明的可校准网络模型，应禁用相关奖励或仅作辅助描述。不能用原始 flow payload 冒充链上消息长度，也不能把合成拓扑的代理成本写成实测时延、能耗。第一阶段不依赖 Intel 拓扑才能成立。

## 8. PPO 保留方式与必须核验的学习链路

保留 PPO 网络、动作选择和服务接口。第一轮候选对照包括旧 Candidate-only；新机制的去 PPO 消融则必须使用同一套容量估计、候选集合和可见历史，最终只替换选择器。

### 必须解决的事项

1. **跨批收益。**当前离线代码对有动作的每个批次设置最后动作 `done=True`，而共享任务大量成本发生在后续批次。需要改成真实序列终止、明确截断 bootstrap，不能仅把所有 done 改为 False。
2. **没有新状态的批次。**这类批次仍有执行与排队成本，应计入上一决策之后的回报，不能直接跳过。
3. **时间尺度。**若采用事件驱动决策，把两次动作间各执行窗口的成本累计起来，同时记录时间/窗口间隔；折扣和 bootstrap 使用一致尺度。
4. **同批多个新状态。**按固定顺序放置并更新虚拟账本；定义批次成本如何归属，避免给每个动作重复计入整批总成本。
5. **信息一致。**注册名单不等于未来访问权重。PPO与规则获取相同的合法历史、预测和容量信息。
6. **观测与模型版本。**需要让 PPO 能区分当前队列、预计预留、任务预计规模等相关因素。若现有向量容纳不了，就扩展并版本化；不能为了保持维度把不同单位塞进旧字段而不说明。
7. **去留依据。**看独立工作负载中的稳定增量及训练、推理代价；不是看训练 reward 是否上升。

第一版不重新设计 PPO 核心优化算法。若只在候选 mask 增加容量规则，也不能把规则产生的收益全部归给 PPO。应增加“同样预测信息＋贪心”对照。

## 10. 数据分割和公平比较

### 10.1 有 PPO 时

保留训练、验证、最终评估的职责。生成配置、特征尺度、任务统计、容量和选模规则用开发数据确定，验证集调参，最终评估冻结方法后运行。

可控仿真使用互不重用的环境随机种子；训练种子、数据种子、部署种子、系统重复编号分别记录。可以增加冻结的分布外压力场景，但不能只挑主方法赢的场景。

### 10.2 无 PPO 时

不必为了形式保留一个“神经网络训练集”，但规则若有参数、统计预测或容量校准，仍需开发/校准数据和独立评估数据。调规则和最终报分不能使用同一批结果。

### 10.3 账本初始化协议

建议主实验采用独立部署场景：冻结算法后，在独立评估轨迹的固定预热前缀运行该方法，以同一输入构建它自己的账本、队列和历史；随后连续评估，不在分界处重置旧任务。各方法因自身决策形成不同状态是允许的，但数据、预热长度和重置规则必须相同。

若另外做“现有账本延续”的时间切分，应明确初始账本来源，不能混合报告为同一种协议。同一任务跨窗口保持地址；实际新任务创建时才计一次首次放置。评估结束后需要统一排空待处理交易，并说明窗口末新任务的后续观察范围。

旧 D3 全量及旧评估结果已用于开发诊断，不再称为完全未触碰的最终测试。可作为已公开的历史验证场景。几千次放置是否足够不能由一个固定阈值判断，需看有效决策覆盖、环境独立重复、任务复杂度和后续访问；扩大独立任务生成比重复同一轨迹 epoch 更有意义。

## 11. 实验矩阵、指标与判断门槛

### 11.1 基线分层

| 类别 | 方法 | 回答什么 |
|---|---|---|
| 基础对照 | Hash、Random、MinState | 随机/静态/只看账户数的效果 |
| 亲和对照 | 注册名单/合法历史下的多数设备片规则 | 只追求局部访问亲和会发生什么 |
| 已有方案 | 原 Candidate-only、现有 Heuristic、NSshard-adapted | 相对已有系统改善多少；改编方法明确标注 |
| 核心强基线 | CAP-now | 正确考虑当前放置后容量，是否已经足够 |
| 机制候选 | CAP-reserve | 活跃任务未来需求预留是否带来增量 |
| 学习增量 | 与对应规则共用信息和候选的 PPO | 选择器是否有额外价值 |

第一轮只运行少数方法：Hash、Candidate-only、CAP-now；通过后加入 CAP-reserve 与 PPO，避免一开始组合爆炸。所有方法在同一任务数据和相同身份模式下执行。

### 11.2 场景参数

初筛可用共享参与数 1/2/4/8（不超过设备总数）、稳定/阶段变化/不可预测访问、低/临界/过载容量压力等少数代表场景。数值是开发起点，不是论文选定参数。参与设备是否跨片另行报告，不按分片布局专门挑选主方法容易获益的成员。

之后再逐项扩展任务到达率、生命周期重叠、访问份额偏斜、设备规模、分片规模、拓扑条件。不能同时改变所有因素后把收益归给一个机制。极端热点、均匀共享和无共享场景保留，用于说明方法边界。

### 11.3 主指标与约束

- 早期离线：跨片交易数、总 stage、最大分片绝对 stage、队列及超载记录、每状态决策数、fallback、预测误差。
- 正式链上：完成交易数与覆盖率、可持续吞吐曲线、均值/P95/P99 延迟、墙钟时间窗口内积压和最忙片绝对工作、决策耗时。
- 若实现通信计量：每原始完成交易的 Relay 字节及总量；重复/失败发送另列。
- 预留机制：容量超额次数/持续时间、实际与预测需求偏差、过度预留、任务结束后是否释放。

固定输入 250 TPS 的完成吞吐接近 250，不能证明服务容量提高；要通过输入速率扫描及队列是否持续增长来评价容量。尾部排空单独报告，不能用最终全部完成掩盖过程拥塞。

比较采用同环境种子的配对结果，先给逐环境差异，再给汇总和不确定性。PPO 训练随机性与链上系统重复分开；同模型重跑不是新增训练种子。交易、区块不当作独立实验重复。

### 11.4 提前停止扩大投入的条件

1. 身份、阶段、时间或信息泄漏检查失败：先修正定义和实现，不扩大实验。
2. 小规模未来参考都显示几乎没有容量约束下的改善空间：重新审视工作负载/问题；未来参考只作诊断，不能进线上策略。
3. CAP-now 已接近参考，而 CAP-reserve/PPO 无稳定增量：不继续堆训练时长；保留规则作为主方法候选。
4. 只有单一对象、单一种子或单一有利场景贡献改善：报告贡献分布与边界，不直接写成稳健效果。
5. 改善仅来自更多可见信息、不同数据或不同部署：补齐公平对照再判断。

不预设“超过 1% 就值得保留”这类统一标准。事先约定主指标和容许的尾延迟/容量代价，再结合系统噪声、置信区间及训练成本判断实际意义。

## 14. 论文贡献的定位

可作为候选贡献的是：有限信息下任务首次放置的明确建模、按实际阶段定义容量并计入放置后的全片影响、对活跃任务后续需求的因果预留，以及对应的低开销决策机制和公平验证。

以下单独不足以证明创新：把 IP 改名为任务、增加几个特征、换用 Ethereum、把贪心改成 PPO、重复实现已有负载均衡或仅搭建数据生成器。容量预留和预测贪心也有近邻研究，需要逐项核对差异，不把一般思想当成全新贡献。

PPO 有稳定增量时，论文解释何种动态性需要学习以及代价；规则效果更好时，可以采用规则主线，但必须有可验证的机制增量，不能只依靠“去掉 PPO”。本方案是优先验证路线，是否足够投稿要等文献差异、强基线和独立测试证据形成后判断。

可核对的研究背景：[SPRING](https://doi.org/10.1145/3589334.3645386) 已使用 DRL 做状态放置并在 Ethereum 交易上评估；本项目保存的 [NSshard 原文](E:/project_iot/block-emulator-main-iot/NSshard_Low-Cross-Shard_Sharding_via_Account_Partitioning_for_Blockchain-Based_IoT.pdf) 也使用 Ethereum 交易。它们说明数据来源可以选择，但不能证明本方案仅换数据就有新颖性。
