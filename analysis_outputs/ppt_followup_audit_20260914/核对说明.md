首次放置关联数都在1至3之间。所有已完成结果10决策日志也得到同样结论。当前数据上的 flag 是无区分信息的常量，可作为后续版本的冗余特征删除；不能只从输入列表删除后继续直接加载原203维模型。新规格应同步调整Python、Go、网络输入维数和检查点元数据；重训或验证等价权重转换。保留旧模型用于复现时维持原203维结构。删除一个恒零特征并不能解决奖励/任务结构问题。

## 3. 对五条原因的核查

1. 状态键包含设备、对端、服务、协议；全量数据中，每个窗口内每个状态对象均只对应一个owner。规则强有结构依据。若只优化跨片/总阶段数并允许owner同片放置，同片可达该执行图的0跨片下界；实际AnchorOnly并非“严格只跟owner同片”的理论策略，不要把它39.8%的结果当成理论下界。
2. 多锚点特征与单owner实际执行的区别成立；训练和评估都可以使用sidecar。划分数据窗口或冻结模型不会自动删除多锚点信息。每个窗口重新冷启动。
3. 固定owner热点成立，测试窗口最热owner分片占比0.636868，共1,273,736条。但当前执行方向为 `state_object -> primary_owner`，应说“固定设备锚点分片上的必要执行”，不宜称为“设备发起的必要源端执行”。
4. 只能说部分解决。当前模拟和阶段统计按真实sender/recipient计算，跨片各计1阶段；最近窗口num、候选负载和阶段热点筛选已使用阶段口径。但全局balance/hotspot及旧方差列仍用折算负载，通信代价仍是距离、链路质量、字节量构造的代理，局部同片奖励仍基于多锚点。代理指标与实际资源、时延目标没有完全一致。
5. 跨批信用分配问题仍存在，已有具体代码与最小运行验证。不能仅凭“首次看不到未来”断言强化学习无法优化；强化学习可以学习预期收益，当前更具体的问题是回报链在批次处被截断。

## 4. 当前回报路径

三个冻结PPO模型元数据均为：gamma=.99、GAE lambda=.95、tx_batch_size=1000、PPO更新阈值batch_size=1024个动作、reward_mode=iot_dense_balanced、action_reward_scale=.1、capacity_backlog_mode=0、backlog_penalty_weight=0。

全局奖励：`.55*R_cstr + .30*R_balance - .10*C_comm - .05*P_hotspot`。
动作奖励：`.1 * clip(.65*clip(r_local,-1,1) + .35*clip(R_batch,-1,1),-1,1)`。
配置 local_reward_weight=0 会在密集奖励模式被提升至至少0.65。

GAE：
`delta_t = r_t + gamma*(1-done_t)*V(s_next) - V(s_t)`；
`A_t = delta_t + gamma*lambda*(1-done_t)*A_next`。

关键路径：

- `offline_env.py:1417`：旧对象不再产生放置动作。
- `offline_env.py:1870`：本批全局奖励混合给本批动作。
- `offline_env.py:1896`：每个交易批次的最后动作done=True。
- `train_offline.py:340`：只在本批动作之间连接next_state，保留done。
- `train_offline.py:923`：多个批次动作累计到1024才更新，但没有取消各批终止边界。
- `ppo.py:135`：终止边界同时截断bootstrap和GAE递推。

最小运行：将第二批奖励放大100倍，第一批两个动作的return仍分别为0.2881、0.2；实际SpringOfflineEnv中，x首次出现产生1个动作，下一批10次重复访问x产生0个动作，buffer样本数不增长。

全量数据中发生在对象首次出现批次之后的交易：训练2,462,328/2,500,000=98.49312%；验证437,180/444,019=98.45975%；测试1,949,894/2,000,000=97.4947%。这些访问仍计入后续批次统计，可能影响其他新动作、共享网络学习或整窗模型选择，但不会通过当前GAE链直接归因到该对象的首次放置动作。

在线路径不同：Go有有限延迟反馈聚合（6个epoch跨度或最多8次匹配、权重0.85^j），不是完整生命周期回报；且本次归档系统测试均SpringOnlineTrain=0，不能用在线代码解释离线模型已得到完整跨批反馈。
