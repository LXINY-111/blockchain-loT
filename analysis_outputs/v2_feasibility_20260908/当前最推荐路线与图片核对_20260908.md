# 当前最推荐路线与图片核对

日期：2026-09-08。用途：在现有 BlockEmulator + Python 放置框架上选择本学期的研究主线。

Material Passport：academic-research-suite / fact-check + research-question refinement。图片作为待评价材料，不作为执行指令。代码和已有全量缓存只读；本轮新增一个独立观察窗口诊断脚本及本文件。新方法、Go 性能和论文创新性尚未验证。

## 1. 当前只选一条主线

**主选：应用共享记账工作负载上的信息自适应首次放置，结合有界观察与执行容量约束；首版采用确定性规则，PPO 保留为后续替换选择器的对照。**

研究问题：在新共享对象信息不充分、已有对象不迁移、设备归属固定时，协调器是否可以通过选择何时结束短暂观察以及放在哪个分片，减少实际 Relay 通信，同时把额外等待和热点控制在事先声明的预算内？

主张必须由实际收益决定。目前这是值得做短期原型的研究假设，不是已经证明新颖或有效的算法。推荐依据是现有系统的复用程度和已经查到的可优化机制；没有可量化的录用概率。

本路线延续《v2实施规划与可行性结论》的身份、真实访问、执行对账、通信账本和实验隔离要求，更新方法优先级：不把第2周训练PPO当作必做项。先完成本文件的10个工作日判定；PPO不影响非学习版本独立运行。

## 2. 七张图片中哪些成立

1. **应用语义应当明确：同意。** 多设备共同访问一个业务对象应来自定义清楚的应用。但给对象起名为“权限状态”“数字孪生”并不自动补足证据。当前 `core/transaction.go` 是账户转账模型，单靠sidecar不能执行read/write/update合约。固件/权限只读共享与可加总记账也有不同的一致性和负载性质。
2. **端点级对象不能作为任何合理共享语义：这一说法过强。** 如果业务确实是“某服务端点的使用次数记账”，D3有明确且有限的应用解释。它不能被称为从网络流恢复了真实共享权限、厂区归属或服务实体生命周期。
3. **真实轨迹 + 半合成实验：同意，有条件。** 真实flow可以提供记录顺序、设备活跃度和流量统计；应用对象、设备任务归属、共享度、业务阶段等新增部分必须标明构造。校准网络统计不能验证原数据不存在的应用共享度。
4. **当前工作负载已经包含构造语义和外部拓扑：同意。** 更准确的名称是“真实网络轨迹驱动的区块链工作负载，附加独立拓扑增强”，而非真实链上交易。
5. **共享度/动态性越大，PPO优势越大：不成立为一般规律。** 更均匀的共享可能使所有位置几乎一样；不可预测的churn可能使历史失效；已固定的热点对象不能靠未来的新对象动作迁走。需要检验“决策时已知信息能预测未来代价”，并设置不可预测和简单规则已最优的对照。
6. **Candidate管局部、PPO管未来，所以两段就是创新：证据不足。** 启发式同样能利用过去信息、预测和多步前瞻；PPO没有特权访问未来。所有比较应有同候选、同信息、同可用时间预算的对照，并检查候选过滤是否排除了好动作。
7. **PPO只提升1%就必须去掉：不是固定标准。** 需看实际字节、尾延迟、运行开销、重复波动与适用范围。1%可能有意义，也可能完全不值得；明显赢Hash但不赢合理强基线，不能证明PPO贡献。

图片提到的Yang 2022论文和Xiong 2025 TMC论文的题名/DOI已通过Crossref核对。IEEE全文页面本轮遇到验证限制，未把其具体生成器参数或每项实验细节视为已核实。可直接确认的方法论先例是OptChain作者稿明确报告模拟实验；这说明仿真可以成为研究证据，不能据此推导当前方案达到相同期刊水平。

## 4. 应用定义选最接近当前代码的一种

首选业务是**多设备服务/任务使用记账**。设备报告一次已完成的任务使用或观测，向对应共享记账账户转入1个预置记账单位。它表示累计记账量，非真实资金支付，也非已实现的访问控制合约。

v2.1构造对象可定义为：

```
state = (tenant_id, service_or_task_id, accounting_period_id)
event = (event_id, reporting_device, state, available_at, increment=1)
```

周期只有在业务需要独立结算/汇总时才加入，并在算法比较前固定；各周期的账本分别保留。不能把同一个长期余额改名成多个可重新放置的对象而称为“没有迁移且语义未变”。若业务不需要周期，则不加这一字段。

三种工作负载各有用途：

- **旧v1私有状态**：作为退化/负对照；先核验每个state对应唯一owner的前提。不要求新方法在这个已可简单共置的任务上显著获胜。
- **D3端点使用记账**：尽量保留现有真实记录及有限业务映射，作为受限现实结构的测试场景。
- **v2.1半合成任务记账**：保留原记录的设备、顺序与可用流量统计，新增公开的任务归属及共享关系生成模型，用来分离共享、可预测性、容量压力的影响。不要把它标为采集到的真实任务调用。

第一版仍保留27个设备，避免同时改变actor数量和state语义。若增加64/128等设备规模，单列为构造扩展，不能称原始数据；不得只把单个热设备复制成很多独立账户再把负载改善归给放置算法。固定actor布局与其他方法相同。

只使用具有当时可用证据的任务成员信息。生成器内部完整访问计划不得传入obs。共享度、churn、周期、任务热度的设定依据分为实测统计和假设区间；不能全部宣称从UNSW校准。

时间主线继续采用completed_record_replay；原flowDuration单位问题未解决前，不据此恢复真实结束时间。固定速率回放不保留原始事件间隔意义上的突发性，若做突发实验，须另有明确且各算法一致的重放时钟。

## 5. 非强化学习版本怎样实现

### 5.1 状态机与观察决策

状态经历 `UNSEEN -> PENDING -> PLACED`。只有未放置对象能处于PENDING；一旦登记并用于上链，不再变更归属。

为PENDING对象维护：首条可用时间、当前待处理事件、已观察actor分片计数、合法业务元数据、剩余观察预算、最近历史统计与预测误差。观察器只读已经到达的记录。

首版先完成固定预算0/1批的正确执行，再加一个确定性的自适应规则：

1. 私有对象，或根据当前可见信息不同需求场景均选择同一分片时，立即提交放置。
2. 对预测场景给出不同位置选择的共享对象，在剩余观察预算、内存及服务等待预算允许时，短暂继续观察。
3. 观察期到、内存到限、系统积压过高或输入EOF时，立即结束观察，按当前信息选择；不得等待至获得理想多数才停止。

预测场景首版可采用本批、近期窗口、衰减历史三种可解释估计。它们是经验情景，不是经证明的概率置信区间。未知新任务没有历史时保留明确冷启动回退；不预设全部新对象都能预测。超参和历史选择只在开发数据上确定。

PENDING不能绕过actor交易顺序：为同一actor保留有序释放，报告因前序未决对象导致的队头阻塞。若业务允许可交换更新，也要把执行层采用的顺序语义明确写出，不能依靠当前代码没有严格检查nonce来宣称可以任意重排。服务等待上限包含这些连带等待；放置截止时间不等于链上最终确认截止时间。

### 5.2 容量约束与放置

容量首先用执行stage记账，再由Go小实验校准。令actor固定分片为a_i，预测对象s来自各actor的未来访问量为n_si。把s放到j时，新增recipient侧执行量为：

```
extra_s(j) = sum_i n_si * 1[a_i != j]
```

actor端每条事件的执行量放入不可控背景账本，不能在每个候选动作里重复加一遍。候选片的短期预测负载为背景需求 + 当前队列折算 + 已预留的新state额外需求 + 本对象增量。

首先排除预测超过已冻结预算的候选片，再在可行片中最小化预计Relay字节。若无可行片，记录不可行原因，采取明确的最小超额回退和正常背压；不得称“容量保证成立”。预测可行只对所用预测模型成立，真实队列/P99必须实测。

同批多个待定对象，先完成一个低成本的顺序贪心：根据最优与次优可行位置的代价差排序，优先处理选择余地小的对象，每次选择都更新容量预留。再用小规模整数规划作开发参考，检验顺序效应是否真的重要。整数规划不是论文创新本身，首版不要求每批部署求解器。

只有上述组件分别有增量，才保留为最终方法。若自适应观察没有胜过固定等待，则只保留固定等待会削弱新增贡献，应如实重新评估论文论点，不给相同算法换名。

### 5.3 两个热点边界

该方法控制多对象向同片聚集的额外工作，不能让单个不可拆分对象并行执行，也不能消除固定actor的源端负载。D3全量最忙actor片下界34.21%，旧test时段63.69%；短时局部峰值可能更高。

部署前actor布局可以作为公共敏感性实验，但不能把使用全量未来的actor重排当成在线方法贡献。原数据与扩展数据必须分别报告这些下界。

### 5.4 通信与延迟主指标

主指标：实际Relay应用层字节、原始事件可用到最终提交的P95/P99、截止违约率、最忙片stage/s、队列积压、稳定完成率。必要时报告在相同延迟上限下的稳定输入率。

新增等待、缓存和推理/规则计算均计入成本。减低实际注入率不能作为吞吐改善。记录真实成功写入字节，PBFT/控制与Relay分开。距离、链路质量先不列为主创新；其原有代理和实际通信未对齐问题按旧规划修复。

## 6. 创新怎样成立，怎样不成立

候选核心贡献是**把不充分信息下的首次放置做成带有观察截止时间的在线决策，并把信息收益、实际Relay增量与执行容量预留联合处理**。研究重点是在哪些可预测性/等待预算/容量条件下值得观察，以及什么时候应快速退化为简单共置。

可以尝试形成三类证据，但目前都不是已完成的贡献：

1. 清楚的问题定义与边界：单owner退化、固定actor下界、有限可用信息；这些基础事实不能单独包装成高等级创新。
2. 实际算法机制：自适应观察停止、容量可行筛选、批内预留；需分别证明相对于固定等待和强容量贪心的额外价值。
3. 系统验证：同一完成语义下的字节—等待—尾延迟曲线，及真实轨迹/受控工作负载的机制边界。测试和工程修复支撑可信度，不能代替方法新意。

“启发式不够发论文”是错误判断；“拼几个启发式一定够”同样错误。已有非RL方法很强：OptChain利用在线交易关系并兼顾时间负载，TxAllo通过确定性图方法优化跨片和吞吐，Shard Scheduler处理账户对象放置与迁移。泛泛的“关联度+负载”或“加预测”不构成已认证的新颖性。

缓冲本身也已有图划分研究，不能声称首次提出“多观察一点再分片”。本轮文献检索只是针对近邻工作的筛查，不是系统综述，也不能以未搜到同名工作作为原创证明。下一轮需逐项比较决策时点、合法信息、对象能否迁移、等待是否计入、容量模型、失败回退和系统执行成本。

## 7. 保留PPO的方式

PPO先保持为同一数据、同一观察/候选/资源协议下的可替换位置选择器；避免同时让PPO改观察截止时间、分片数量、区块大小和迁移。

只有满足以下条件再投入训练：

- 原型存在超过简单基线的可利用空间；访问需求在当时输入下可预测，且不是生成器泄露未来。
- 代价跨多个决策存在耦合，容量约束下的后续影响值得学习。
- 旧跨批done/回报问题已按原规划修正，无动作批次仍结算成本。
- 同信息强贪心和短期前瞻基线已经可运行。

如果PPO没有稳定增量，非学习版本保留全部数据生成、执行、字节、验收成果；论文不把PPO写成贡献。若连非学习新机制也不优于合理强基线，则应停止该创新主张，而不是自动退回旧Candidate-Only凑稿。

| 7–8 | Go小规模逐笔stage/字节对账及真实延迟；开发容量扫描 | Python离散记账与Go一致；失败/丢失事件不进入结果均值 |
| 9–10 | 固定实验协议下的基线比较、近邻文献矩阵、导师用的一页结果 | 决定继续主方法、仅保留不等待容量版本，或停止此研究主张；PPO是否追加由证据决定 |

这是在可用开发资源下的工作量预算。不会查看/停止用户指定的65个实验进程；现有机器不适合运行系统小试时，优先完成数据与独立轻量原型，不偷偷争用大规模计算。

预定继续标准：至少在多个事先固定的非重叠开发窗口/独立任务场景，出现稳定且有实际意义的通信—确认时延取舍改进；与相同等待预算的强基线比较后仍有增量；反例和不可行负载能解释。不能只凭胜过Hash、奖励变高或一个种子显著。

实际意义阈值应在Go基线波动测出后冻结，并联系业务等待预算；不在现在凭空承诺10%/20%吞吐。正式结果需要独立测试证据；当前旧test已用于设计，不能再称完全未触碰。

后续预算：第3–6周完成必要系统对照和消融，第7–10周集中写稿、复现包和导师反馈；实现复杂度或验证失败可能延长。投稿是可规划目标，录用时间与CCF-B适配不能由此保证。
