## 1. 需要做出的研究取舍

首选研究问题：在有业务含义的IoT服务使用记账工作负载中，首次放置共享状态能否在强贪心方法之上，减少实际跨片通信开销，并在容量允许时改善尾延迟？先证明任务有可优化空间，再证明PPO的额外作用。

主线保留首次放置、不迁移、固定actor归属；以实际跨片交易和Relay应用层字节为直接可测目标。物理距离、链路质量先作为有独立假设和验收标准的扩展。禁止同时重构迁移、复制、一致性协议、GNN、大型PPO网络和动态actor划分。

若简单方法已接近可达下界，应收缩PPO的贡献表述，考虑预测加贪心或系统方法。不要为保留PPO而削弱基线、删掉困难流量或创造无业务意义的新对象。

## 2. v2业务与数据契约

### 2.1 事件、actor与state

推荐最小业务：服务使用记账。监测代理依据一条已完成且可用的双向flow，提交一次使用记录；actor为文件所属设备对应的报告主体。不能把它直接称为该flow的网络请求发起者。

共享对象保存某服务的累计使用记账单位。最小执行版本每事件Value=1：actor扣除一个预置记账单位，service账户增加一个单位。service的增量Balance就是累计事件数；若沿用全账户统一初始余额，最终核验必须减去初始余额，不把初始资金当作流量。此为明确的仿真应用抽象，不是实际DNS合约或现实代币支付。

原始payload、包数和时长留在sidecar作工作负载描述；它们不等于Transaction序列化后的长度，不直接决定CPU指令量。若后来需要真实字节负载，须另外定义每事件上链的记录格式并测量编码长度，不把整条网络flow的payload默认为上链数据。

候选定义D0/D1/D2/D3及固定端口表见《设计约定》。结合原始MAC全部缺失、旧primary IP依赖全量推断的实际结果，推荐从D3的因果服务记账定义进行小规模验证：当前记录两端只有一个符合固定服务端口/协议规则的单播端点时共享，否则采用设备私有端点对计数。D2保留为保守但仍依赖旧身份推断的对照，D0只作“删device”的诊断。D3与旧状态粒度不同，因此各算法必须在同一D3工作负载内比较，不能把D3相对v1的变化全部算作PPO增益。

正式canonical key至少包括：schema版本、部署/观测域、规范化远端服务IP或稳定服务标识、服务端口、传输协议、应用服务类型。不同观测域的同一个私网IP不能无条件合并。IP被复用时，没有服务实体证据只能称端点级共享；不能声称解析出了真实服务生命周期。

本轮sidecar缺少ipProto。D3业务明确对同一应用服务的TCP/UDP等传输作合计记账，因此它的key不依赖ipProto；正式生成器仍从原始flow补齐此元数据以供分层报告。若另选按传输协议分开的业务，必须使用不同StateDefinitionID并重做统计。

### 2.2 方向与身份解析

1. 首选设备注册信息、PCAP中MAC与当时IP映射或已知DHCP租约；保留证据来源与有效时间。
2. 已有“全文件最常见IP”仅可用于本轮历史描述；在线特征不能默认使用未来全量统计。
3. 原始flow的srcMac/dstMac缺失时，记录缺失事实；不能以文件名MAC补造每行通信方向。
4. 明确outbound时取远端dstIp/dstPort，明确inbound时取远端srcIp/srcPort；这只能得到远端端点，是否服务端还需要协议/端口或协议参数证据。
5. D3不需要根据旧primary IP判断actor方向：actor是文件报告主体，服务端点由当前记录唯一匹配端口规则产生。它不能被描述为已恢复真实请求发起方向。组播/广播端点、不匹配服务及双方均匹配的歧义记录保留并私有回退；单播且唯一匹配的控制服务也只能在明确记账语义下计入。可以追加明确筛选的子集实验，但所有方法必须使用同一子集，并报告覆盖率与被排除的负载。

### 2.3 一条原始记录只对应一条事件

不把相关gateway、cloud、service_group等上下文锚点展开成额外交易。同一双向flow的src/dst统计不自动拆成两条事件。不同设备捕获文件可能记录同一网络交互：主业务若是每设备观测报告，这些是不同报告；若声称每次网络服务调用，则需先建立跨文件去重证据。两个口径不能混用。

### 2.4 时间可用性和批次

**主线采用completed_record_replay**：输入是一条已经完成并导出的flow记录；回放器按固定输入率逐条向协调器交付记录，available_at是回放交付时间。此时该条记录的payload和协议标签已可用，未来记录不可见。原始time仅用于确定轨迹顺序，不能宣称是在原始网络首包到达时作决定。这个定义与本轮按tx_index统计相容，也不依赖尚未核实的flowDuration单位来产生到达时间。

推荐closed_batch模式：按回放available_at稳定排序，每1000条构成已到达批次，末批在EOF闭合；先收齐再决策。250条/s时，最早到达记录约需等待4s收齐本批。必须计入这部分等待，不能只从决策后的注入时间计延迟。本轮没有采用100ms超时；若后续引入超时/不同批量大小，需要重新统计可见信息，并让全部基线使用相同规则。生产回放与后续注入采用明确的流水线/速率控制，不能把收批等待额外串行化后仍声称实际输入率为250。

发布原始事件时间、记录回放可用时间、批次闭合时间、实际注入和最终提交时间。当前统计仅验证相同分组下的访问结构与stage记账，没有模拟这些墙钟耗时。

**可选真实时间扩展**：官方描述确认time为首包时间，Dryad README将flowDuration标为秒；但本地原始例子的数值与120s分流规则需要进一步核对（见实测报告）。未确认导出单位前不自动改为毫秒，也不直接按秒生成结束时间。基于流超时的在线导出还需等待确认流结束，例如最后包之后的超时/刷新周期；不能只把首包时间加duration便声称当时一定已经可用。这个扩展不阻塞明确声明的完成记录回放主线。`官方字段说明`（历史产物，已清理）

### 2.5 冷启动与有历史的部署分开报告

- 冷启动：state首次在网络记录中出现时没有它自己的历史，只能用当前已闭合批次及合法静态上下文。
- 有历史的新部署：部署区块链之前的被动网络观测可以提供服务使用历史，但该时期不参与链上放置和计费。部署后state首次上链时使用这个过去的统计，是合法预测输入。
- 已上链对象不能在测试起点重新放置却仍宣称连续在线运行。不迁移模式下已有归属必须保留。
- 独立部署窗口允许从空账本开始；必须明确是多个部署情景，不能把它们当一条连续系统轨迹。

## 3. 两个核心风险怎么处理

### 3.1 热点：先识别可移动部分与不可消除下界

对窗口W，令A_j为归属于分片j的actor事件数，N_s为state s的访问量。固定actor、不可拆分state、同片一次stage/跨片两次stage时：

max_j L_j >= max(max_j A_j, max_s N_s)。

若输入率为λ，则最忙分片至少需处理λ·max(max_j A_j,max_s N_s)/|W|个stage/s。这是必要条件，不是充分稳定性证明，更不是实测容量。还需考虑PBFT、Relay、序列化、执行、网络和尾部排空。

按下列顺序处理：

1. 先保留服务区分和私有回退，防止把整个gateway或协议误合成一个巨型state。
2. 多个独立state造成热点时，用基于实际stage和队列的负载感知放置，限制向已忙分片继续聚集。
3. 单个不可拆分state超出任意一片容量时，首次放置不能解决。应改研究范围、提高明确的资源预算，或另行研究拆分/复制；不要继续调PPO。
4. 若业务确为可加总计数，可设计K个显式分区计数器与一个只读聚合视图。分区必须对应合法独立记账桶；合计一致性、查询扇出、合并/结算事务、元数据与存储成本均需计入。状态拆分可缓解state热点，但不自动缓解固定actor的源分片热点。
5. 若actor固定哈希碰撞形成热点，可以把“部署前、仅根据过去负载的actor分片”作为独立公共前处理，让所有算法共享同一结果。单个actor本身过热依然是下界。actor子账户会改变nonce/余额和业务语义，属于后续研究，不作为本学期默认改造。

容量验收使用最忙分片绝对stage/s、积压斜率、P95/P99、完成率与排空时间。禁止只看Jain、归一化最大份额或奖励分数。

### 3.2 通信：优先做真实可记账的Relay字节，再做拓扑扩展

**必做版本C1：真实应用层通信量。** 在统一发送入口记录成功写入的应用层字节，按消息类型、源/目的分片、唯一消息/交易标识分类。交易发送、Relay、PBFT、控制消息分别列出；跨片量改变必须能在实际消息或字节账本中复核。应用层字节不能称为含TCP/IP头、重传的物理网卡字节。部分写入记录实际n字节；失败和重试分别记录；写成功也不等于接收端已成功解析，若声称送达量需接收侧对账。

最小动作相关成本为C_relay=Σ实际Relay消息编码字节。对固定映射变化的手工轨迹，改变state分片应产生预期的Relay差异。Python使用经Go编码夹具校准的估计B(message_type, fields)，正式结果使用Go实测；不把估计值冒充实测。

**条件扩展C2：有向拓扑成本。** 先固定分片执行位置/网关与actor入口，定义哪个网络路径由state选择改变。actor→其固定分片的入口成本可能是常量；actor分片→state分片的Relay路径才可能随动作变化。只增加设备与服务距离特征并不能建立这条因果关系。

Intel数据的链路概率是有向的、全时段平均的成功率。缺边保持unknown，概率0视为不可达，不用反向边替代，不用1/(1+distance)填成“实测链路”。本轮Σ1/p最短路径只表示忽略ACK等条件下的期望逐跳发送次数代理，不能直接称时延、焦耳能耗或完整ETX。

若要报告拓扑加权成本，使用明确标注的ΣRelay字节×路径代价，同时报告可达流量覆盖率与缺边；不同网关映射和容量参数做敏感性实验。若要声称实测时延受链路质量改善，须在传输/调度层加入可复核的链路带宽、延迟和重传模型并验证，这一扩展排在基本结果之后。

Python和Go必须读取同一个成本契约。禁止一端payload，另一端payload+packets+duration；禁止混合字节、包数和时长而没有量纲解释。原有固定输入权重可作为描述性特征，但从“动作优化后的通信成本”主指标中移除。

## 4. 决策与学习的最小重设计

### 4.1 环境状态与动作

actor地址固定映射，state地址为唯一放置目标。batchRelated按state→本批实际actor计数构建；权重由已到达访问数计算，不能把context anchors加入访问分母。

输入包含：本批actor分片分布、过去窗口的服务访问预测、预测置信/冷启动标志、各片已观测stage服务率/队列、对象已知大小、候选分片动作相关Relay成本。账户数量只能作为存储规模辅助项，不能替代事务队列负载。

主基线先全16片动作。候选过滤单独消融：实际访问者所在片加若干低队列片；不得根据未来最优片筛候选。全部被过滤时有确定性回退并记录原因。PPO与Candidate-Only使用相同候选集和信息。

### 4.2 强基线顺序

1. Hash：相同v2对象、相同actor布局。
2. FirstActor：首次已知actor同片，揭示简单共置收益。
3. FirstBatchMajority：已闭合首批访问量最多的actor分片，确定性同票规则。
4. HistoryMajority：只用部署前/当前之前的服务访问统计预测未来主分片；同时比较短窗口和指数衰减历史。已有本轮实测显示，全前缀累计多数在新部署旧test窗口的跨片率为11.1051%，反而高于首批多数的9.9316%，所以不能预设历史越多越好。超参数只在开发窗口选定。
5. LoadAwareGreedy：用同样历史预测与真实队列估计未来各片stage增量，先满足容量/积压约束，再最小化预测Relay成本；完整记录评分与选择。
6. Candidate-Only：与PPO完全相同筛选器，采用预先固定的贪心决策。
7. NSshard-adapted/SPRING相关基线：核实原算法边界、输入信息、重划分能力和预算后接入；不能只比较名字相近的自定义方法。

另列FutureMajority的跨片理论下界和使用未来流量的负载分配参考，明确标为oracle/离线参考，不能充当在线可用算法。只考虑跨片的下界为Σ_s(N_s-max_j N_sj)，不表示同时最优的负载或网络代价。

### 4.3 回报必须跨越没有新放置动作的批次

推荐事件驱动的决策轨迹：只有首次放置产生策略决策动作；批次执行和没有新state的批次仍推进环境时间并产生成本。一个批次内多个新state顺序放置，中间动作没有执行成本，最后一次放置后执行本批；后续无动作批次的成本累加到尚未闭合的transition，直到下次决策或episode终止。

每条transition保存obs、action、old_log_prob、value、累计reward、next_obs、delta_batches、terminated、truncated、policy_version。令累计奖励为R_k=Σ_h γ^h r_{t+h}，则TD项为R_k+γ^Δ V(next)-V(obs)。GAE递推也使用与逻辑批次一致的折扣；同批中间放置Δ=0，不能凭空消耗一个批次折扣。

先用完整有限episode、γ=1、λ=1验证精确回报；训练稳定性阶段再在开发集固定折扣/GAE参数。把批末全部标done=True的旧方式禁止沿用。真正终止与采样截断分开：截断保留bootstrap，终止不bootstrap。参考`PPO官方实现`（历史产物，已清理）的区别，但不直接复制其单步时间模型到本任务。

推荐首版episode由一个固定部署窗口和排空阶段构成，策略在整段采样期间冻结，采样结束后更新。先做100k事件窗口，再按state后续流量覆盖扩展至200k/更长。报告回报窗口覆盖的后续访问比例，不声称有限回报已优化完整203天生命周期。不要在旧policy产生的待结算动作尚未完成时更新参数并混入新policy轨迹。

若一个episode完全没有新动作，只输出系统指标，不伪造PPO样本；其成本如果承接前面的放置，应归到上一待结算transition。批次平均奖励复制给所有新动作可以作为初始共享回报，但要报告高方差，并用消融检验局部shaping是否扭曲物理目标。

### 4.4 奖励初版

先将跨片stage/Relay字节作为可对齐主成本，队列积压积分或最大利用率为容量约束项。各量按冻结的有单位参考量归一化。通信若与跨片数完全线性重复，不将其伪装成独立创新目标。

取消无证据的“局部奖励至少占65%”强制下限；旧权重只保留在旧模型协议中。热度使用到达/执行stage率，不能用账户数代替。候选覆盖、奖励均值、entropy、KL是诊断指标，不代替实际系统收益。

```python
build_observation(state_id, closed_batch, past_history, placement, telemetry, cost_spec) -> Observation
# 只能读已闭合批次、过去history、冻结actor布局和已观察队列。

choose_placement(observation, candidate_mask, policy) -> PlacementDecision
# 每个state只调用一次；选择的是分片，不是某个actor。

commit_placement(decision, placement_registry) -> None
# 已存在state必须拒绝重新放置；同一事件所有执行端看到一致映射。

account_stage_cost(events, placement_registry, actor_layout) -> StageLedger
# 所有原事件恰有一次actor stage；跨片恰有一次recipient stage。

advance_until_next_decision_or_end() -> Transition
# 不跳过无动作批次的成本；包含delta_batches、terminated和truncated。

validate_run(manifest, event_ledger, message_ledger, replica_states) -> ValidationResult
# 状态不是PASSED/SKIP的字符串猜测；各必需子项有结构化计数和结果。
```

Go的v2流程须在创建/哈希交易前确定Actor、State、Value和EventID。不要继续通过事后交换Sender/Recipient改变已有TxHash的含义。EventID作为稳定源记录标识保留，网络重传使用同一业务EventID，Relay阶段使用显式阶段标记；唯一事件计数与发送尝试计数分开。
